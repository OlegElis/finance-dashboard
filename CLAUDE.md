# Finance Dashboard — правила проекта

> Дашборд управленческого учёта для ГК ОПОРА. Один файл `index.html` (весь HTML/CSS/JS,
> без фреймворков и сборщиков), хостинг GitHub Pages. Данные — Google Sheets API (read-only,
> API-ключ), лист `RawData`. Устройство вкладок, имена функций, поля состояния и структуру
> данных смотри в коде — здесь только то, чего в коде нет: договорённости, запреты,
> нестандартные решения и причины их принятия.

## Общие правила

- **Автопуш**: всегда пушить в GitHub автоматически после каждого коммита, без вопросов.
- **Дефис, не тире**: нигде не использовать «—», только «-» (в коде, UI и в чате).
- **Фильтры per-tab**: у каждой вкладки свои фильтры (`_tabFilters[tab]`). Изменение фильтров на одной вкладке НЕ влияет на другие.
- **Изоляция вкладок**: работая с одной вкладкой, НЕ трогать код других. У каждой вкладки есть набор «защищённых» функций (`renderBank`, `bankFillTxn`, `renderBflModel` и т.д.) — не менять их при работе над чужой вкладкой.
- **Локальная проверка перед пушем**: дашборд нельзя открывать через `file://` - Firebase Auth не работает вне http/https. Поднимать локально: `python -m http.server 8000` в папке проекта, открывать `http://localhost:8000`. В Google Cloud Console → API-ключ → HTTP referrers должен быть разрешён `http://localhost:8000/*` (уже добавлен).

## Данные и источник

- Google Sheets API, `valueRenderOption=UNFORMATTED_VALUE&dateTimeRenderOption=SERIAL_NUMBER`. **Даты приходят Excel-серийными числами** → `parseDate` конвертирует. Первая строка `RawData` — заголовки; индексы колонок фиксированы (`COL` в коде), перестановка колонок молча ломает отчёты.
- **Данные собираются через IMPORTRANGE** из источников. Во время пересчёта импорта шапка временно приходит пустой / `#ERROR!` / `Loading…` — поэтому сверка структуры листа (`connectAndLoad`, эталон в localStorage `fin_rawHeaders_{sheet}`) идёт ТОЛЬКО по «полной валидной» шапке (15 непустых, без `#`/`loading`), иначе была бы ложная тревога.
- **Медленное открытие - это ПЕРЕСЧЁТ формул, а не объём данных** (замер 30.07.2026 в браузере на живой странице): холодный запрос ОДНОЙ ячейки формульного листа - 14 894 мс, он же по прогретому листу - 376 мс; весь лист (60 700 строк, 23,5 МБ) - 2 539 мс ответ + 1 266 мс тело, `JSON.parse` 40 мс. Лечится заливкой листа значениями - `apps-script/freeze-rawdata.gs` (формулы уезжают на `RawData_src`, дашборд читает `RawData` со значениями). Три страховки в скрипте: не писать транзитное состояние IMPORTRANGE, не затирать при обвале числа строк вдвое, снимок предыдущих значений в скрытый датированный лист (последние три). **Замер ПОСЛЕ заливки (31.07.2026): 1 ячейка 482 мс холодная / 352 мс тёплая (было 14 894 / 6 196), весь лист 2 320 мс ответ + 1 293 мс тело (не изменилось - это сборка ответа и сеть, а не пересчёт). Открытие ~18,7 с → ~3,6 с, разброс холодный/тёплый упал с 8,7 с до 130 мс: пересчитывать больше нечего.** ⚠ **Кэш RAW в IndexedDB по этому результату НЕ делаем** - экономия трёх секунд не стоит 23,5 МБ финансовых данных на диске, переживающих закрытие браузера (схема кэша ниже - на случай, если понадобится). ⚠ **Загрузка по периоду скорость НЕ чинит** - сэкономила бы около секунды из сорока; отложена до переезда на базу, не возвращать как «оптимизацию». Оставшиеся 3,6 с растут ЛИНЕЙНО по числу строк (ответ 2,3 с - сборка 60 737 строк на стороне Google, тело 1,3 с - сеть): при удвоении базы это ~7,2 с, при утроении ~10,8 с. Возвращаться к разговору о загрузке по периоду имеет смысл, когда открытие перевалит за 8-10 секунд, а не раньше. Справочники (`loadBflDeals`/`loadOfferRef`) идут через `Promise.all` - они независимы, а последовательные `await` складывали два круга ожидания.
- **Кэша RAW между открытиями НЕТ и пока не будет** (решение 30.07.2026). После заливки значениями остаётся ~3,6 с, а кэш стоил бы 23,5 МБ чужих финансовых данных на диске, переживающих закрытие браузера. Проект уже горел на том, что новый пользователь видел RAW предыдущего (см. `appLogout`) - дисковый кэш воспроизводит это в худшем виде. Если после перезамера окажется медленно, схема согласована: IndexedDB, ключ `email + имя листа` (у сотрудников свой `_dataSheet`), удаление в `appLogout`, показ из кэша с честной надписью «данные от ЧЧ:ММ, обновляю…», инвалидация по `sheetId`, по расхождению шапки с эталоном, по возрасту сутки и кнопкой обновления.
- Архивирование: данные тянутся через отдельный Apps Script (замороженный XLSX у источника); настройки бэкапятся кнопкой в дашборде (общее меню: `downloadBackup` - данные+config целиком).
- **Архив настроек БДР** (⚙ Действия, админ): отдельно от `downloadBackup`. Бэкапит `config/*` ЦЕЛИКОМ по ЧЁРНОМУ списку `BACKUP_EXCLUDE=['sheets','forceLogoutAfter','backupLog']` (новые ветки попадают автоматически - `anomalyAck`/`sheetAccess` появятся позже, жёсткий список их бы потерял). Файл `{format:'opora-config-backup',version,exportedAt,by,branches,config}`. Восстановление (`pfBackupRestoreOpen`): проверка format/version (version выше поддерживаемой → отказ), превью (ветки в файле + ветки в базе, которых в файле нет; записи планов; замороженные месяцы - счёт ТОЛЕРАНТЕН к массиву/объекту у `plansBaseline`), слово `ВОССТАНОВИТЬ` (точный регистр), **авто-скачивание текущего состояния перед записью** (страховка), запись по веткам через `_fbSetSafe` (локальные кэши обновляются своими листенерами). Авто-предложение архива (`pfBackupPrompt`, не блокирует) - перед заморозкой месяца и `planFillAllFact` (на обычный `planSave` НЕ вешать). `config/backupLog={lastExportAt,by}` - бейдж «💾 Архив настроек: N дн. назад» в шапке БДР при >30 дней/никогда. Транзакции (Sheets) в архив не входят.
- **Листы-справочники**: `RawData_BFL` — только БФЛ; `RawData_ID_Offer` — сделки ВСЕХ направлений (для сверки `ID_Offer` в Аномалиях/Депозитах). Матчить сделки **по системному ID** (число до «|»), а не по полному `ID_Offer`/ФИО/№ договора — их могут изменить, ID нет. Нормализация ID — `_arNormId`.

## Дизайн-система

- Все цвета/шрифты — CSS-токенами в `:root`, **не хардкодить hex** в компонентах (точные значения — в коде). Стиль: спокойный, плотный, данные-первичны.
- **Цвет = знак значения**: доход/прибыль зелёный (`--income`), расход/убыток красный (`--outcome`), остаток ДС оранжевый. Заголовки секций — нейтральный `--text2`, НЕ акцент.
- Бренд-акцент — графитово-синий `--accent` (был фиолетовый `#7c4ddb`, заменён по просьбе). Только для активной навигации/чекбоксов/логотипа/линий графиков, не для декора.
- Шрифты: IBM Plex Sans (интерфейс) + IBM Plex Mono с `tabular-nums` для ВСЕХ чисел. В `.report-table` 1-я колонка — текстовый лейбл (sans), остальные — числа (mono).
- Chart.defaults — mono, оси серые. Маркетинговая палитра завязана на легенды-чипы — не трогать без синхронизации легенды и графика.
- **Математический ноль гасится в ФОРМАТТЕРАХ, а не в расчётах** (`_z0`, порог 0.005 = полкопейки). Сумма 5212 перемещений даёт −1,49e-8: значение верное, врёт только знак, и вывод получался «-0,00». `_z0` стоит в общей `fmt`, в `numClass` (иначе хвост красит математический ноль в красное) и в 14 локальных форматтеров денег (`f2`, `fmt2`, `fmtR`, `money`) - они общую `fmt` не зовут. Суммы при этом остаются точными.

## Подсказки (единый компонент)

- **Подсказка с ЧИСЛАМИ - только через единый компонент** (`_tipAttr` в разметку / `_tipSet` из JS → `_tipShow`, узел `#uiTip`). Нативный `title` рисуется системным шрифтом, из CSS не управляется, и выровнять в нём числа невозможно: `padStart` не держит столбик, потому что пробел и цифра в системном шрифте разной ширины. В компоненте выравнивание держит **сетка** (`uit-grid`, 2 или 3 колонки; третья - например доли в процентах), числа моно с `tabular-nums`.
- **Что переводить, а что нет** (решение принято на инвентаризации 171 подсказки): на компонент - только те, где есть ЧИСЛА или многострочный список. Подсказки на кнопках/фильтрах/чекбоксах (что делает контрол) и пояснения к колонкам и режимам ОСТАЮТСЯ нативным `title` - там нечего выравнивать. «Операции: <период>», стадия сделки в Дебиторке, фильтр Аномалий, KPI «Исполнение YTD» - это подсказки клика и пояснения, они нативные СОЗНАТЕЛЬНО (числа у YTD стоят в самой карточке, а не в подсказке).
- ⚠ **Узел живёт в `<body>` с `position:fixed`, позиция считается от `getBoundingClientRect()` якоря.** Внутри скроллящегося тела таблицы (`.table-scroll`, тела карточек Банка) подсказка обрезалась бы по `overflow` - ровно то, на чём горели выпадающие списки фильтров. У краёв окна разворачивается внутрь (вправо/вверх).
- Показ - ОДИН делегированный слушатель на `[data-tip]`: подсказки переживают любой ре-рендер таблиц, свои слушатели пришлось бы навешивать заново. Гасится уходом курсора, Esc, кликом (тоже capture - клик обычно перерисовывает таблицу или открывает модал, а подсказка стоит по координатам и висела бы над новым содержимым; на тач это главный сценарий залипания), скроллом (capture - внутренние контейнеры до `window` не всплывают), `beforeprint` и `blur`. На тач-устройствах показ по тапу с автоскрытием 4 с (курсор там не уходит, иначе залипнет навсегда). `@media print` гасит узел - на печати подсказок нет по определению.
- `z-index:100003` - выше всех оверлеев проекта (потолок был 100002): подсказка обязана быть поверх модалов.
- ⚠ **Значения в `_tipAttr` передавать СЫРЫМИ** (`_htmlEsc` он делает сам). Предварительный `esc` даст двойной эскейп - «&amp;amp;» в именах.
- ⚠ Где подсказка меняется ПОСЛЕ рендера (редактор планов: «⤓ заполнить фактом», undo) - только `_tipSet`, и снимок undo хранит `data-tip`, а не `title`. Иначе поверх компонента ляжет нативный `title` и подсказка будет выглядеть по-разному до и после нажатия кнопки.
- **Графики (Chart.js) свой tooltip НЕ меняют на компонент** - там выравнивание уже держится (холст, моношрифт, `padStart` работает). К стандарту приведён только ВИД, и задан он ОДНИМ местом - `Chart.defaults.plugins.tooltip` рядом с `Chart.defaults.font`. По графикам не размазывать: иначе следующий график заведут со старым видом и никто не заметит.
- **Числа в подсказке - ПОЛНЫЕ, всегда.** Подсказка это место, где читают точное значение (правило «не сокращать числа» здесь без исключений). Сокращения `М`/`К` остаются на подписях ОСЕЙ и надписях на холсте (`moneyTick`, `km`, `abbr`, `kfmt`) - там полные не влезут и по ним не считают. ⚠ Где на одном графике лежат деньги и количества (юнит-экономика) - целые без копеек, дробные через `fmt`, иначе у количеств появится «12,00».
- ⚠ `displayColors:false` в подсказке дневного графика Банка - НЕ косметика: с цветными квадратами Chart.js сдвигает строки ТЕЛА вправо, а footer нет, и разряды разъезжаются.

## Безопасность (по аудиту)

- **`_htmlEsc(v)`** — ЕДИНСТВЕННЫЙ способ вставлять данные из Sheets (ячейки RAW) в `innerHTML`/`onclick`. Без него — хранимый XSS через ячейку. Применять во ВСЕХ новых рендерах для любых данных-лейблов.
- **CSV-экспорт** (`registryExportAI`): текст, начинающийся с `= + @ -` или таба, префиксовать апострофом (защита от формульных инъекций в Excel).
- **`_isAdmin()`** = текущий пользователь == `ADMIN_EMAIL` (`o017ev@gmail.com`). Гейтит запись общих `config/*` и админ-UI. Реквизиты `config/sheets` пишет ТОЛЬКО админ, сотрудники читают — иначе при правиле «запись = админ» каждый вход сотрудника ловил бы отказ. Попап лимитов реквизитов для не-админа — только просмотр.
- ⚠ Остаётся по дизайну: **Sheets API-ключ в исходнике** (нужно ограничение по referrer в Google Cloud Console). Клиентская модель доступа — **барьер от посторонних, а не строгая изоляция** (продвинутый юзер может запросить чужую вкладку; строгий вариант — Apps Script-прокси).

## Надёжность (по аудиту)

- **`_fbSetSafe(path,val,label)`** — ЕДИНСТВЕННЫЙ способ писать в `config/*`: при отказе правил БД/офлайне показывает alert «сохранено только локально». Раньше сейвы были fire-and-forget — «✓ Сохранено» врало, планы терялись при следующей загрузке.
- Каждый рендерер обёрнут в try/catch (`renderActiveTab`) — упавший показывает заглушку с текстом ошибки, а не мёртвую вкладку.
- **Logout обязан сбрасывать сессию**: `appLogout` гасит презенс и обнуляет `_appBooted`/`_dataSheet`, чтобы следующий вход перегрузил данные СВОЕЙ вкладки. Раньше новый пользователь видел RAW предыдущего. `watchForceLogout` сравнивает с `_flAuthMs` (обновляется на каждом входе), а не с `auth_time` первого входа.
- **MutationObserver-ловушка**: мобильные хелперы (`watchMobileCards`) и переинжект пресетов (`_setupPresetObserver`) слушают `#mainContent` и срабатывают на каждый ре-рендер. ⚠ Их колбэки НЕ должны безусловно мутировать DOM (писать `innerHTML` только при реальном изменении; сводку фильтров обновлять по data-sig) — иначе observer зацикливается.
- **Именные ловушки при правке кода**: `presetApply` - пользовательские пресеты (дропдаун), `setPreset` - пресеты периода; не путать (старые быстрые дат-чипы и функция `applyPreset` удалены). Глобального `esc` нет (он локален в каждой render-функции) - для эскейпа вне рендера свои хелперы (`_pesc`, `_htmlEsc`, `_dEsc`).
- **RTDB превращает числовые ключи в МАССИВ.** `config/plansBaseline/<year>/<month>` Firebase может сохранить как `{1:{...}}` или как `[null,{...}]` - зависит от плотности ключей. Читатели (`_baselineMonthsMap`) должны быть толерантны к обеим формам: `Object.keys()` работает и там, и там, но проверка `Array.isArray()` с ранним выходом отбрасывает валидные данные. При записи нормализовать к плоскому объекту (иначе форма-массив затирается на `{}` и теряет уже сохранённые ключи).

## Авторизация и доступ (Firebase Auth, email+пароль + Google)

- Дашборд закрыт экраном входа. Пользователи email/пароля заводятся **в консоли Firebase**, не в коде.
- **Белый список** (`resolveAccess` - та же функция, что резолвит роли, отдельной `checkAllowed` НЕТ): доступ если email == `ADMIN_EMAIL` ИЛИ в `config/allowedEmails`/`config/sheetAccess`. Применяется ко всем способам входа; не прошёл → `signOut` у вызывателя.
- **Доступ по ролям (вариант A)**: `resolveAccess` → админ видит `RawData`; email в `config/sheetAccess` → свою вкладку; в `allowedEmails` → `RawData`. Это разрез «у каждого свой отчёт», НЕ строгая изоляция (таблица/ключ общие).
- **fail-open**: если Firebase/CDN недоступны или нет ключей — дашборд открывается без входа (барьер, а не защита; данные и так тянутся по API-ключу из исходников).
- **Рубильник «Сбросить сессии»** (админу): пишет `config/forceLogoutAfter`, каждая сессия слушает и делает `signOut`, если метка новее её `auth_time`.
- ЦФО/ответственные = люди с доступом: список ФИО берётся из `config/names` (отдельной панели ЦФО нет - объединена с «Управление доступом» по просьбе «все, кому дан доступ, должны быть ЦФО»).
- **Иерархия ЦФО (2 уровня)**: `config/cfoHierarchy = { "<ФИО подчинённого>":"<ФИО руководителя>" }`, один уровень вложенности; руководитель без записи = верхний уровень. Задаётся колонкой «Руководитель» в панели «Доступ», пишется через `_fbSetSafe` (`_cfoHierSave`), кэш localStorage + `startCfoHierarchySync`. Ключи по ФИО (как `_planOwners`) - при переименовании ФИО в панели записи `cfoHierarchy` И `planOwners` мигрируют на новое ФИО (`accessSavePanel`, матч по email). Ключ ответственности `_planOwners[dir||подстатья]` НЕ меняется. Свод ЦФО («Исполнение по ЦФО», собирается в `renderPlanFact` в `window._pfCfoModal`, открывается модалом `pfCfoOpen` - отдельной `cfoHtml` НЕТ) двухуровневый: строка руководителя = свои подстатьи + сумма подчинённых, раскрывается (`cfoToggleMgr`, чистый DOM-тоггл - не ре-рендер, чтобы `<details>` свода не схлопывался); ИТОГО считается по СЫРЫМ `agg` (листовым), поэтому факт ИТОГО не меняется от иерархии. Выписка (`cfoStatementGen`): для руководителя галочка «Включить подчинённых» → секции по людям («Свои подстатьи», затем каждый подчинённый) + ИТОГО по блоку; жёсткий фильтр по владельцу сохранён (подчинённый не видит чужих подстатей). Защита от цикла А→Б→А: `_cfoMgrOf`/`_cfoSubsOf` игнорируют самоссылку, дерево - строго один уровень.

### Правила RTDB (Firebase Console) — задаются вне кода, без них молча ломается
- `config/.read` = `auth != null`. ## Ключевые учётные решения (иначе выглядят как баг и будут «исправлены» обратно)

- **`120_Ввод начального остатка` — НЕ выручка НИГДЕ** (глобальный хелпер `isOpeningBalance`, единообразно в ОПиУ/БДР/ФОТ/Структуре/Юнит-экономике). Это входящий остаток, а не доход; раньше раздувал ЧП и завышал %-планы. Прочие `120_` (реализация имущества, депозит, возмещение) — выручка. **ОПиУ и БДР считают выручку одинаково.**
- **«Вывод чистой прибыли» (код 127, дивиденды) НЕ входит в расходы и в ЧП** — вынесен в отдельную секцию «Распределение прибыли» ниже линии ЧП (в ОПиУ, БДР, Структуре расходов). Иначе ЧП расходилась с ОПиУ ровно на сумму дивидендов.
- **Проверка после любой правки расчётов БДР (сверка, НЕ константа)**: «ИТОГО РАСХОДЫ факт» в БДР должно совпадать с «РАСХОДЫ» в ОПиУ за тот же период и то же направление. Обе цифры считаются из одного `RAW` разными путями - совпадение доказывает, что расчёт не сломан. Конкретное значение постоянно меняется по мере пополнения базы транзакций, поэтому проверяется РАВЕНСТВО двух отчётов, а не совпадение с фиксированным числом (прежняя контрольная константа устарела и удалена). ⚠ Осторожно: `127_вывод прибыли` в ОПиУ вынесен ниже ЧП, в БДР - в секцию «Распределение прибыли»; сравнивать расходы БЕЗ вывода 127. **Что разводит отчёты и как ловится**: ОПиУ включает списание ТОЛЬКО при точном совпадении аналитики со списком `OPIU_CATS`, БДР считает все списания (кроме вывода 127) - аналитика вне списка (опечатка/регистр/пусто) молча завышает БДР ровно на свою сумму. Два сторожа брака данных: правило `ancat` в Аномалиях + «⚠ Аналитика вне ОПиУ» (`pfAnBadOpen`, счётчик в ⚙ Действиях БДР) - оба по одному `OPIU_CATS`. Расчёт не трогают, показывают строки для правки в источнике.
- **Расчётный транзит почты БФЛ↔САУ** (ОПиУ, чекбокс): виртуальные строки (в Sheets НЕ пишутся), только когда выбран ровно один контур. Кейс: БФЛ + `112_Депозиты и госпошлины` + |списание| ∈ {25000,50000} + непустой `ID_Offer` → транзит **фикс 20000 ₽/ID** (плейсхолдер; при факте заменить на фактические суммы). БФЛ −20000, САУ +20000.
- **EBITDA-корректировки** — непрофильные/разовые расходы; значение аналитики в Sheets должно быть ровно `EBITDA-корректировки`. Тумблер двигает их выше/ниже EBITDA; ЧП в обоих режимах одинакова.
- **Займы сотрудникам — знаковая модель**: `amount = inc + out`; `>0` выдача, `<0` возврат; долг = Σ amount. Нельзя брать возврат как `abs(поступления)` — иначе выдача (+) и возврат (−) оба считаются возвратом и долг задваивается.
- **Календарный `daysB`** (разница `Date.UTC` по локальным компонентам) — в Займах, Дебиторке, Депозитах. Прямое `(b-a)/сутки` занижало на 1 день и давало «−1 дн.» для операций «сегодня».
- **БДР: baseline (`config/plansBaseline`) - замороженный утверждённый план года. Не редактируется никогда.** Прогноз (`config/plans`) правится свободно, baseline - только через «Утвердить план года» (снимок прогноза, только админ, только при сохранённом плане - иначе staged-правки откатились бы по «Отмена», а baseline остался бы с ними). Отклонения (Δ) и KPI «Исполнение YTD» считаются ОТ baseline; «Прогноз года · ЧП» - от прогноза. Причина: план, который можно править задним числом, делает отклонение недоказуемым. %-планы baseline конвертируются в рубли от СВОЕЙ (снимковой) базы выручки (`buildPlanCalc` со своей income-базой), а не от текущего прогноза - иначе замороженный процент поплывёт; `_planIncBaseMonth` (база прогноза) при этом не трогается. Наборы строк (`codeSet`/`incSet`/`vyvodSet`) пополняются кодами из baseline: иначе статью можно спрятать, убрав её из прогноза. UI: 3 колонки «Утверждено | Прогноз | Факт | Δ к утв.»; без baseline колонка пуста, Δ не считается, красный баннер «план не утверждён». Печать (`planPrintOwners`) остаётся прогнозной + штамп об утверждении. **Флаг `retro` (ретроспектива)**: месяц заморожен, но НЕ планировался заранее (план проставлен задним числом = факт; чекбокс при заморозке, поле `retro` в объекте месяца, отсутствие → false). retro-месяцы ИСКЛЮЧАЮТСЯ из «Исполнение YTD · расходы/доходы» (`_planableFrozenMonths`), иначе дают фальшивые ~100%; но ОСТАЮТСЯ в «Утверждено»/Δ/остатке лимита/коридоре графика (цифры верны). Все замороженные = retro → карточки YTD прочерк «нет планируемых месяцев». Пометка 📋 (вместо ⚠) в матрице и выписке ЦФО.
- **БДР, режим «Статья»: строка-статья группируется по c3 подстатьи (`ARTICLE_NAME`), а не по коду статьи.** Причина двойная: (1) разные статьи бывают с одинаковым c3 (`111_ФОТ` и `111_ФОТ (выслуга лет)`) — при группировке по полному `ARTICLE_CODE` `planAgg(c3)` отдавал план всей группы каждой статье, и план в ИТОГО задваивался; (2) ключ берётся от подстатьи, а не от статьи, потому что разворот (`subsOfArt`/`factSubN`) группирует детей по их c3 — иначе на строках с расхождением c3 статьи и подстатьи (ловятся в Аномалиях) статья ≠ Σ подстатей. Пустая подстатья даёт дочернюю строку под кодом статьи (`sn=an||ac`), чтобы не теряться молча. Лейбл строки = «c3 · представитель» (`ARTICLE_CODE` с макс. оборотом в группе). Фильтр по статье работает по c3: выбор одного полного кода тянет всю c3-группу.
- **БДР, 3-й уровень (расшифровка РАСХОДНОЙ подстатьи по «стороне»)**: ФОТ → сотрудник 👤, аренда → объект 🏢, консалтинг → контрагент 👤. Классификация стороны - **ЕДИНЫЙ модульный источник** (`sidesOfSub`/`_sl*`/`_sideUniverse`/`_buildSideFactIdx`), общий для трёх потребителей: выписки ЦФО, редактора планов и сводной БДР (в сводной - третий уровень раскрытия подстатьи). Причина: две копии классификации разъехались бы (как было бы с `OPIU_CATS`); при рефакторе в примитивы числа выписки сверялись байт-в-байт. Матрицы «все месяцы» 3-й уровень НЕ касается.

## Решения пользователя по вкладкам (не откатывать)

- **Юнит-экономика (marketing)**: CPL скрыт (логика в коде сохранена); `112_Распределение КМ` и `112_Транспортные` в CPF не включаются; подстатей `300_Реклама/маркетинг` и `244_Контроль качества` в данных НЕ существует. Направление — одиночный выбор, «Все направления» нет. Для БФЛ количества считаются авто из `RawData_BFL`; тех-специалисты (`EXCL_RESP_*`, по «Кем создана сделка») исключаются из количеств, но остаются в дебиторке.
- **Аномалии**: только жёсткие детерминированные правила (массив `RULES`), без статистики — статистика давала много шума. В правиле «карты АУ/САУ» (`aucard`) карта **СберБанк-1638 Елисеев ИСКЛЮЧЕНА** из `AU_CARDS` — она используется в любых направлениях, а не только АУ/САУ.
- **Аномалии, правило `outsign` (положительное списание) — помечаем, НЕ гасим.** Правило показывает ВСЕ положительные списания (из `where` убран `!isRefund`). Возврат в данных = пара строк (списание −X и рядом +X, тот же контрагент/подстатья/дата), отдельного признака «возврат» в строке нет. Поэтому `+X` не прячется автоматически, а получает подсказку «↩ похоже на возврат · парное списание −X от ДД.ММ.ГГГГ»: ищется ближайшее по дате зеркало в индексе отрицательных списаний (`_negIdx`, ключ `контрагент|подстатья|round(|сумма|)`, по ВСЕМУ RAW — зеркало может быть вне фильтра дат), окно `MIRROR_WIN=366` дн. **широкое сознательно** — ложная пара ничего не прячет, только подсказывает. Лексический `isRefund` (слово «возврат» в подстатье/назначении) — второй источник подсказки, тоже не гасит. Берётся БЛИЖАЙШЕЕ по дате зеркало (не первое в массиве). Подтверждение: админ жмёт «✓ проверено» → ключ `outsign:<хэш строки>` пишется в `config/anomalyAck` (через `_fbSetSafe`, кэш `_anomalyAck` + `startAnomalyAckSync`), проверенные уходят из списка (чекбокс «Показать проверенные (N)» их возвращает с кнопкой «↺ снять»). Хэш строки — по всем стабильным полям (философия «Дублей»); ack — **только админ** (`_isAdmin()` гейтит кнопки; запись `config/anomalyAck` = `ADMIN_EMAIL`). Требует непустого контрагента для матча зеркала (пустой ключ давал бы шум).
- **Дубли**: сравнение ВСЕЙ строки целиком после trim, без исключений. Удаление — только вручную в Sheets (дашборд read-only).
- **Дебиторка БФЛ**: оплата (нетто) = поступления − только `112_Возвраты клиентам`; депозит суда (`120_Поступление депозита`) и перемещения оплатой НЕ считаются. Закрытые стадии ВКЛЮЧЕНЫ по умолчанию (по ним мог остаться долг). Сделки до 01.04.2024 скрыты по умолчанию (старая дебиторка фиктивная).
- **Займы**: определяются по «Реквизиты счёта» содержащему «займ»+«сотрудник»; статья/подстатья не участвуют.
- **Депозиты АУ**: вывод (127) больше не отслеживается — после возврата поток идёт в операционные расходы АУ/САУ.
- **ФОТ / Структура расходов**: «Вывод прибыли» исключён из расходов (иначе итог расходится с ОПиУ).
- **БДР (planfact), раскладка**: на десктопе (>820px) вкладка - флекс-стек фиксированной высоты (`#tabPlanfact`, CSS-блок в head): скроллится ТОЛЬКО `.table-scroll`, фильтр-бар/KPI/заголовок/sticky-шапка стоят. У таблиц `border-collapse:separate` - НЕ возвращать `collapse` (sticky-шапка в таблицах с collapse глючит в браузерах; это и было причиной «уезжающей шапки»). Графики - `<details id="pfCharts">`, свёрнуты по умолчанию, состояние в `_tabFilters.planfact.chartsOpen`, после разворота `pfChartsResize` (чарты создаются при display:none). Мобила и печать - обычный поток (@media).
- **Банк, раскладка и отступы**: вкладка - флекс-стек фиксированной высоты (механика `#tabPlanfact`), скроллятся только тела карточек. Отступы контейнера уплотнены ТОЛЬКО для Банка: `.content:has(#tabBank:not(.hidden)){padding:12px}` (у `.content` общий базовый 24px/`--secpx`, менять его нельзя - он на 18 вкладок). ⚠ **Правило лежит в ОТДЕЛЬНОМ `@media screen and (min-width:821px)`, и это не косметика**: лист A4 в пикселях шире 821, без `screen` уплотнение уезжает в печать. Переводить на `screen` ВЕСЬ общий блок `@media (min-width:821px)` НЕЛЬЗЯ - в нём раскладка Банка и БДР (флекс-стек, sticky-шапки, паддинги таблиц), печать её использует, а `@media print` правит только `height`/`overflow`. ⚠ **Высота вкладки завязана на паддинг `.content`**: `calc(100vh - 80px)` = топбар 56 + 12 + 12 (при паддинге 24 было 104). Правишь паддинг - правь и высоту, иначе освободившаяся вертикаль просто пропадёт. ⚠ **`#tabBank` - флекс-колонка, в ней margin НЕ схлопываются**: `margin-bottom` у KPI складывался с `margin-top` у колонок и давал зазор 12 вместо 6. Единый зазор 8px держится тем, что низ у KPI погашен, а расстояние задаёт ТОЛЬКО верхний margin следующего блока. Освободившаяся вертикаль отдана графикам (`chart-wrap` 228px); таблицы её не теряют - `bank-cols` остался `flex:1 1 auto`. **Графики в ПЕЧАТИ обязательны** (визуализация всего отчёта) и чинятся ТРЕМЯ слоями: (1) `beforeprint`/`afterprint` → `resize()` обоих графиков, продублировано через `matchMedia('print')` (Safari печатает иначе, `beforeprint` может прийти не в тот момент или не прийти); (2) `@media print` кладёт графики ОДИН ПОД ДРУГИМ (`grid-template-columns:1fr!important` - сетка `1fr 1fr` приходит из `@media (min-width:821px)`, а лист A4 шире порога, поэтому применяется и на печати) + `break-inside:avoid`, `chart-wrap` 340px = треть листа на график; (3) `canvas{max-width:100%;height:100%}` + `overflow:hidden` на карточке. ⚠ **`height:100%`, а НЕ `height:auto`**: при `auto` холст брал свою битмап-высоту, переполнял карточку фиксированной высоты и заголовок следующего графика наезжал на предыдущий. ⚠ **Кегль подписей в печати НЕ трогаем**: холст на трети листа во всю ширину физически крупнее экранного, подписи читаются сами. Множитель 1.35 был нужен, пока графики стояли рядом по 200px, и убран как лишний (если когда-нибудь понадобится - только в САМИХ опциях: размеры заданы явно 9/10px, `Chart.defaults` их не перебивает). ⚠ **`_BANK_CHARTS` - ФУНКЦИЯ с живыми ссылками**, а не массив: графики пересоздаются на каждой смене фильтра. Массив строк-имён тоже работал бы (разыменование в момент вызова), но он немой - при переименовании глобальной переменной промолчал бы, а живая ссылка падает заметно. ⚠ В печати скрыты сайдбар, гамбургер, «Онлайн», ФИО и «Выйти» (`.main{margin-left:0}` растягивает контент на лист); заголовок отчёта и строка фильтров ОСТАЮТСЯ - они говорят, что за отчёт и за период.
- **Редактор планов, «⤓ заполнить фактом»**: маркер «план ≠ факт» (подпись «факт X» + янтарная рамка) ставится ТОЛЬКО при ненулевом факте - будущие месяцы без «факт 0,00» под каждой ячейкой (это был оранжевый шум). Маркер - тонкая рамка + бледный фон, не насыщенная заливка. `borderColor` входит в снимки undo (⤓/⌫/↶) - при правке снимков не терять. Строки, где нет ни плана, ни факта - `plan-row-empty` (приглушены opacity, оживают hover/focus, НЕ скрыты).

- **БДР, матрица «все месяцы» - ячейка в 4 уровня**: факт (12px) · утверждено · прогноз · отклонение «−539 066,41 (91%)». Сокращения К/М убраны СОЗНАТЕЛЬНО (правило «не сокращать числа»), все числа полные, флешем вправо в моно - разряды выстраиваются в вертикальный столбик, поэтому справа от числа в уровнях 1-3 ничего быть не должно. Строка отклонения - только при заметном (`PF_DEV_OVER=0.03` перерасход/перевыполнение, `PF_DEV_UNDER=0.05` недобор), в норме её нет. Цвет: доходы `+` зелёный / `−` красный, расходы `+` красный / `−` янтарный. **База отклонения: утверждённое, если месяц заморожен, иначе прогноз**; цвет самого факта считается от ТОЙ ЖЕ базы и тех же порогов - иначе в незамороженном месяце ячейка противоречит себе (факт зелёный к утв., отклонение красное к прогнозу). **Колонка «Год» = СУММА помесячных `devBase` (накопитель `ydb`), а НЕ сумма утверждённого**: при частичной заморозке (янв-июн 🔒, июл-дек нет) сумма утв. сравнила бы годовой факт с базой за полгода. ЧП - цвет по знаку, строки отклонения нет; вывод прибыли 127 получил свой `kind='vyv'` (раньше шёл как `'exp'` и красился как обычный расход). ⚠ `vertical-align:top` на ячейках - НЕ косметика: при дефолтном `middle` соседние ячейки строки с разным числом уровней разъезжаются по вертикали и горизонтальное чтение строки разваливается. Минус в отклонении - типографский U+2212 (`toLocaleString` отдаёт дефис-минус). **Типографика: жирным ТОЛЬКО колонка «Год» и факт итоговых строк.** Подстроки (утв/прог/откл) - вес 400 ВЕЗДЕ, включая итоговые строки: выделяется ФАКТ, а не план. Промежуточного веса 600 в матрице НЕТ: статьи и подстатьи в месячных колонках весом не различаются - их разводит отступ, треугольник разворота и цвет лейбла в первой колонке (пробовали 600 у статей - вернули к 400 по просьбе). - **БДР, сводная (месяц и год): ДВА ПЛАНА РЯДОМ и остаток к каждому.** Двухрядная шапка, 8 колонок: `Статья | Ответственный | План (Утв · Тек) | Факт | Остаток (К утв · К тек) | Статус`. Безусловно гасить НЕЛЬЗЯ - ЦФО-модал зовёт `remTd` внутри строк с `cfoToggleMgr`, там клик по ячейке разворачивает подчинённых. **Стрелка пересмотра плана** у «Тек.»: сравнение по МОДУЛЮ (расходы отрицательные, −134 366 против −73 116 - рост расхода). Синяя `#2563eb` - план ослаблен (расход вырос / доход снизился), сине-серая `#7b8ba3` - ужесточён; красный и зелёный НЕ брать - они заняты отношением ФАКТА к плану, это другая ось. Слот 14px резервируется в ОБЕИХ плановых колонках (`planNum`): будь он только в «Тек.», её число уехало бы на ширину слота относительно «Утв.» и разряды не встали бы в столбик. **Цвет числа «Факт» и бейдж «Статус» - из ОДНОГО примитива `statusOf`**, порог один (`PF_TOL`): свой порог у подсветки дал бы «число цветное, а рядом написано в норме». База приходит аргументом, поэтому при переводе статуса на другую базу цвет переедет сам. Статус считается от ДЕВБАЗЫ периода (заморожен месяц → утверждённое, иначе текущий план, фолбэк на другую сторону). Раньше был жёстко от утверждённого под гейтом `hasBaseline` - в незамороженном месяце говорил «план не задан» рядом с заполненными «Тек. план» и «Остаток к тек.» (асимметрия видна в июле). Девбаза приходит ТРЕТЬЕЙ стороной пары остатка (`{u,t,d}`; `_pickDev`/`_bmDev` собраны из того же `_subOneBaseM` - второй копии правила нет), поэтому база и факт period-matched и статус СХОДИТСЯ с колонкой остатка (раньше сравнивал факт всего периода с базой части периода). От какой базы посчитана строка - в `title` её ячейки. Подсветка «Факта» едет за статусом сама: `factCol` читает `st.col`. **Вес числовых ячеек = уровень агрегации**: итоги 700, статьи 600, подстатьи и третий уровень 400 (`numW`). Инлайн ОБЯЗАТЕЛЕН - `.report-table td` задаёт `font-weight:600` всем ячейкам; в `remTd` вес идёт параметром, иначе пять её веток разъехались бы с соседями по строке. Названия в 1-й колонке не трогаем - там иерархия показана отступом и треугольником. **Клик:** реестр операций открывает ТОЛЬКО «Факт» (и только при непустом `kind` - у итогов и третьего уровня `kind=null`, строка не кликабельна); планы, остатки, статус и ответственный гасят всплытие и стоят с `cursor:default`. **ЧП и вывод 127 - разные основания, не сводить к одному правилу.** Δ, статус, подсветка факта и стрелка пересмотра - это ОЦЕНКА, а оценку к выводу прибыли применять нельзя: у `net` и `vyv` их нет. Но ОСТАТОК - не оценка, а величина («сколько ещё можно вывести по плану»), поэтому у 127 он ЕСТЬ и показан нейтральным серым без светофора; пустым его не делать. У ЧП остаток пуст по ДРУГОЙ причине - она не планируется напрямую (разность доходов и расходов), и «остаток прибыли» не имеет смысла. Формулировка «у ЧП и 127 пусто» неточна: правильно **«у ЧП пусто, у 127 нейтрально»**. Доходы показывают «осталось собрать» (зеркальный светофор). **Ширина:** `PF_COLG` в процентах, Σ **ровно 100.0** (28.0 + 13.0 + 5×9.8 + 10.0) - при <100 Chrome и Safari распределяют остаток по-разному; `min-width` 260/150/132/132/118/118/118/110 (плановые 132 - под слот стрелки) = пол 1138px, ниже ~1416px вьюпорта включается горизонтальная прокрутка внутри `.table-scroll` со sticky-left «Статьёй» (шрифт чисел НЕ уменьшать). **Двухрядная шапка:** 1-й ряд фикс-высоты `PF_TH1` (26px = padding 7+7 + line-height 12), 2-й - `PF_TH2` с `top:26px` ПОСЛЕ `${th}` (перебивает его `top:0`); выравнивание в `th` ставится ПОСЛЕ `${th}`, иначе его `text-align:right` перебивает префикс. ⚠ `mobileCardify` берёт ПОСЛЕДНИЙ ряд `thead` и матчит позиционно (4 ячейки против 8 в теле) - подписи сдвинулись бы, поэтому рендерер ставит `data-label` сам, а `mobileCardify` уважает уже проставленный атрибут.
- **БДР, фильтр ЦФО режет числа по (НАПРАВЛЕНИЕ, подстатья), а не по подстатье целиком.** Мульти-владельческие подстатьи - НОРМА (одна подстатья, разные ЦФО по направлениям: 111_ЗП АП ×3, ЗП ОМ ×2). Первая версия owner-cut (per-sub, `subOwnerPass`) под одним ЦФО показывала полный факт подстатьи, включая чужие направления - неверная атрибуция. Теперь единые примитивы (`_dirSubPass`/`ownDirsOf` + карты `_pdExp/_pdInc/_pdVyv` по ключу `dir||sn` + `_subFactP/_subFactM/_subPlanP/_subPlanM`, generic по `recsFn/cvt` → работают и в baseline) агрегируют подстатью ТОЛЬКО по направлениям, где её владелец проходит `selOwn`. Через них идут ВСЕ потребители: факт/план/baseline статьи (год+месяц), дочерние подстатьи (сводная И матрица), остаток, модал (`_pfOwnSubs`=`[{sub,dirs}]`, `pfShowTxn` фильтрует операции по owner-passing dir). `subOwnerPass` остаётся только для ВИДИМОСТИ строки/разворота. **Ключ карт - `sn=an||ac` (как `factSubN`), НЕ `an`:** пустая подстатья (дефект) даёт `sn=ac` → `_planOwners[dir||ac]` пуст → NOOWN, иначе она выпадала бы из сумм по «(не назначен)» и контроль ломался. `expByDirSub` (свод ЦФО) остаётся по ключу `an` - его не трогаем. Контроли (держать): (а) Σ подстатей = статья; (б) числа под фильтром ЦФО одинаковы в «месяц» и «все месяцы» (один per-dir примитив на оба); (в) Σ ИТОГО по всем ЦФО, включая «(не назначен)», = ИТОГО без фильтра; (г) модал = число строки. Без фильтра (`selOwn` пуст) все примитивы отдают полную подстатью - поведение и числа прежние (факт→`factByCode`, план→`planExp`).

Без фильтра полные суммы = строкам таблицы, ИТОГО обычные.

## Ловушки по вкладкам (корректность/UX — не «упрощать»)

- **БДР: «плана нет» ≠ «план равен нулю». В итогах НЕЛЬЗЯ `reduce((s,r)=>s+(r.plan||0),0)`** - сумма пустых схлопывается в 0, и Δ итоговой строки считается ОТ НУЛЯ (незамороженный месяц без утверждённого плана давал «Утверждено -0,00» и красный перерасход на весь факт). Слой планов дисциплину соблюдает (`planMonth`/`planYear`/`planAgg`: `tot=null`, `tot=(tot||0)+v` только при `v!=null`) - её надо ПРОДОЛЖАТЬ в итогах через `sumOrNull(arr,get)`. Нулевой план валиден и обязан доходить до итога как `0`, поэтому по всей вкладке проверять `!=null`, а НЕ truthiness: ловушки, уже пойманные один раз, - `sumPlan||null` в вызове `dRow`, `sumIncPlan>0?…:revRow.plan` (подменял нулевой доходный план общим планом «Выручка»), `(incTotalPlan!=null||sumPlan)` в `netPlanV`/`netBaseV`, `sumPlan?fmt():'-'` в KPI. В колонке «Остаток» по той же причине `hasP=planM!=null` (без `&&Math.abs(planM)>0.0001`), а ветка «лимит на исходе» требует guard на ненулевой план - иначе `rem/Math.abs(planM)` даёт `Infinity`.
- **ОСВ, переходящее сальдо**: скрытые периоды ДО первого видимого вкатываются в «Сальдо нач.» ТОЛЬКО в `rowCalc`; цикл `buildRow` стартует с `lastVisIdx = pksAll.indexOf(visPks[0]) − 1` и докатывает лишь скрытые периоды МЕЖДУ видимыми. Иначе при обрезке разреза «день» (лимит 62 дня) получается двойной счёт сальдо.
- **Банк, extra-фильтры**: списки значений в дропдаунах строятся из `dataBase` (снимок ДО применения extra-фильтров), чтобы выбор одного значения не «схлопывал» список остальных.
- **Банк, фильтр-бар: «ID Offer» и «Контрагент» УДАЛЕНЫ СОЗНАТЕЛЬНО, не возвращать.** Они про операции, а на вкладке остался только свод по счетам; поиск по офферу и контрагенту живёт на вкладке РЕЕСТР, где для этого полный набор фильтров. Вычищены по всей цепочке (разметка, фильтрация в `renderBank`, списки значений, сводка, `× сбросить`, дефолты, закрытие по клику/Esc, `_filterSig`); обёртки `bankOffer*`/`bankSecond*` сняты, общие хелперы `_bankExtra*` остались - ими пользуются «Реквизиты счёта» и «Направление». Порядок бара: Реквизиты счёта · ФНС · Направление · Будущие оплаты (основные фильтры свода - первыми). Старые пресеты с ключами `offerIds`/`secondSides` применяются без ошибок: лишние ключи оседают в `_tabFilters.bank` и никем не читаются.
- **Банк, ПЕРЕМЕЩЕНИЯ между своими счетами - отдельная сущность и на графиках, и в своде.** Учётная схема (менять её не надо): перемещение записано ПАРОЙ в колонке ПОСТУПЛЕНИЙ - уход со счёта это ОТРИЦАТЕЛЬНОЕ поступление, приход положительное; списаний в этих строках нет. По компании пары сходятся в ноль, но по ОТДЕЛЬНОМУ счёту пара распадается (второе плечо на другом счёте), и до правки «Поступление» по счёту было занижено на объём транзита, а зелёные столбики на графике уходили вниз. Единый источник разбора - `isMoveRow`/`bankSplit`, через них идут ВСЕ четыре точки агрегации (первичная в `renderBank`, помесячная по году, `bankRebuildChartData`, `bankUpdateDays`). Цвет - `BANK_MOVE_COLOR='#a86b1a'` и на графиках, и в колонке; **НЕ брать `--orange` (#e8862b)** - им нарисованы линия «Остаток ДС» на том же графике и светофор остатка в таблице. **«Остаток ДС» НЕ меняется**: линия считается от `inc+mov−out`, что тождественно прежнему `incВсе−outВсе`. Порядок колонок свода: `Поступление · Списание · Перемещения · Итого` (поступление и списание - пара, которую сравнивают взглядом, разрывать её перемещениями нельзя). Валовые обороты - в единой подсказке (`_tipAttr`, см. раздел «Подсказки»), ДВЕ строки без «сальдо»: сальдо уже в самой ячейке, подсказка добавляет, а не повторяет. Раньше это был нативный `title` с выравниванием через `padStart` - в системном шрифте пробел и цифра разной ширины, столбик не держался. ⚠ **Две ловушки, обе ловились:** (1) `hasMove` обязан учитывать `mov` - иначе счёт, где ТОЛЬКО транзит («Займы сотрудникам»), исчезает из свода; (2) `saldo` обязан включать `totMov` - по компании он ноль и KPI не меняются, но под фильтром одного счёта пара распадается и «Сальдо» разошлось бы с «Итого Общий итог».
- **Банк, дневной график: клик по столбику НЕ уводит с вкладки.** Переход в Реестр по клику был заведён и ОТКАЧЕН - Реестр существует отдельной вкладкой, уводить с графика не нужно; `bankDayToRegistry` удалена, курсор над холстом `#chartMonth{cursor:default}` (общий `.chart-wrap canvas{cursor:pointer}` трогать нельзя - он на 18 вкладок). Клик по столбику МЕСЯЦА на верхнем графике - оставить, он переключает дневной график.
- **Банк, KPI «Доля оформленного»** (между «Счетов» и «Cash Runway»): поступления по счетам ФНС=Да к базе из ЧЕТЫРЁХ каналов. Метрика СТРУКТУРНАЯ и рисковая, не операционная. База - только ПОСТУПЛЕНИЯ (налоговое обязательство возникает на входящем потоке), списания в неё не входят, перемещения исключены явно (`isMoveRow`). ⚠ Фильтр ФНС на карточку влиять не должен - под «Да» она всегда показывала бы 100%; при активном фильтре карточка даёт прочерк. Цвет нейтральный: нормы у показателя нет, светофор ТОЛЬКО у стрелки - покрашенная доля стала бы ежедневным укором и перестала бы замечаться. Разложение по каналам - в подсказке (канал · сумма · доля), у строки «всего» процента НЕТ (100% там по построению, а с округлёнными долями спорит). **В названиях не использовать слова «официальный», «неофициальный», «серый»** - в системе есть точная формулировка «до налогового оформления», она описывает состояние, а не намерение; дашборд видят сотрудники и он уходит в PDF-архивы.
- **Банк, «Доля оформленного» - ДВА режима, и сравнение только там, где базы одинаковые.** Режим 1 (сравнение есть): период не задан, пресет «Этот год» (то же окно) и пресет «Прошлый год». Окно текущего года - `янв-<последний месяц С ДАННЫМИ>`, а НЕ по календарю: 1 августа при данных по июль окно «янв-авг» тянуло бы долю пустым месяцем (та же ошибка, что чинили в годовой колонке БДР). **База сравнения - ПРЕДЫДУЩЕЕ КАЛЕНДАРНОЕ ПОЛУГОДИЕ** (`_halfBefore`): для окна янв-июл 2026 это июл-дек 2025. ⚠ **Год-к-году отвергнут и возвращать его нельзя**: он врёт, когда контур запустился в середине прошлого года. У БФЛ оформленный поток пошёл с августа 2025 (июл 20 000 → авг 651 900 → сен 2 363 400), и янв-июл 2026 против янв-июл 2025 давало +18,5 п.п. - арифметически верно, по смыслу «раньше контура не было, теперь есть»; через год цифра рухнула бы без всякого ухудшения. ⚠ Вариант «предыдущие N месяцев подряд» (июн-дек 2025) тоже отвергнут: для БФЛ он захватывает июнь-июль 2025, когда контура ещё не было. Границы полугодий фиксированные, поэтому база не ползёт вместе с окном. **Исключение - пресет «Прошлый год»: там год-к-году, и это НЕ недоделка.** Правило про полугодие решает проблему ЧАСТИЧНОГО года (окно оборвано текущим месяцем, а прошлогодний отрезок помнит запуск контура), а у полного года такой проблемы нет: двенадцать месяцев к двенадцати, базы одинаковые. Сравнивать полный год с шестью месяцами предыдущего полугодия было бы странно, подпись у пресета своя («2025 к 2024»), перепутать нельзя. Единообразие ради единообразия здесь навредит - не «причёсывать». ⚠ Разная длина отрезков (7 месяцев против 6) допустима - доля это ОТНОШЕНИЕ, длина его не искажает; но подписи обязаны называть ОБА отрезка («янв-июл к июл-дек 2025»), иначе разница длины не видна. Сезонность соседние периоды не сглаживают (в отличие от год-к-году) - для структурной доли это принято сознательно, к вопросу вернёмся, если пойдут ложные колебания. Режим 2 (сравнения нет): произвольный период - сдвиг отрезка на год попадает в другие условия. Мелкая строка ОБЯЗАНА называть период - так режимы различаются с одного взгляда. ⚠ **Режим определяется `preset`, а НЕ непустотой дат**: `buildFilterOptions` при загрузке заполняет поля дат полным диапазоном выгрузки, поэтому пустыми они не бывают НИКОГДА и проверка на непустоту давала режим 2 всегда - стрелка не появлялась ни разу. Отдельный флаг «период трогали» заводить НЕ надо, им и является `preset`: его выставляют все пути смены периода (даты руками → `'custom'`, кнопка пресета → `setPreset`, сброс Банка → `'all'`, пользовательский пресет → `setPreset` из `presetApply`). Сравнивать текущие даты с дефолтными тоже нельзя - верхняя граница ползёт с каждой новой операцией. Стрелка - в процентных ПУНКТАХ с подписью «п.п.» (разница 28,9% и 24,6% это 4,3 пункта, а не 17%); порог «менее 0,5 п.п. - серая вбок» считается от ОКРУГЛЁННОГО значения, иначе 0,49 рисуется как «+0,5 п.п.» серым рядом с настоящими 0,5 зелёным.
- ⚠ **Признак ФНС для карточки берётся из карты «счёт → признак» по ВСЕМУ набору без дат**, а не по срезу периода: признак принадлежит счёту, а не периоду, иначе счёт с «да» только в строках 2025 года в 2026-м уехал бы в другой канал и сравнение годов сравнивало бы разные классификации. **Известное следствие, это НЕ баг**: если у счёта признак заполнен только вне выбранного периода, карточка отнесёт его к каналу по этому признаку, а свод внизу вкладки - к другой карточке, потому что свод определяет признак по ВИДИМЫМ строкам. Расхождение между блоками возможно и означает дефект данных (незаполненный признак), а не ошибку расчёта.
- ⚠ **«Доля оформленного»: ВВОД НАЧАЛЬНОГО ОСТАТКА ИСКЛЮЧЁН из базы. Решение принято осознанно 31.07.2026, оно расходится со вторым правилом проекта - не «упрощать» обратно.** Столкнулись две верные трактовки одной строки. Первая: остаток проведён поступлением НАМЕРЕННО, это деньги на счёте, и по ФНС он классифицируется наравне с остальными (так считает свод Банка, KPI «Поступления», «Сальдо», «Итого Общий итог» - там остаток учитывается и учитываться должен). Вторая: `120_Ввод начального остатка` - НЕ выручка НИГДЕ (глобальный `isOpeningBalance`, единообразно в ОПиУ/БДР/ФОТ/Структуре/Юнит-экономике). Для карточки вопрос был только в ЗНАМЕНАТЕЛЕ: она измеряет структуру ВХОДЯЩЕГО ПОТОКА, а стартовый остаток потоком не является. Выбрана вторая трактовка по замеру: 19 строк за апрель 2024 на 13 235 805 (17 счетов, крупнейшие на ФНС=Да - ИП Болотов/Альфа 7 268 402, СИБСУДЭКС 995 093, ГУ СЭ 491 304) задирали 2024 год с 25,2% до 32,7% (+7,5 п.п.) на базе 61 млн против 74 млн. С артефактом ряд читался как «росли от низкой базы», без него - «упали в 2025 и восстанавливаемся» (25,2 → 22,3 → 29,0). **Сравнение 2026 к 2025 от этого НЕ зависит** (остатки заводились только в 2024, стрелка +6,7 п.п. в обоих вариантах) - правка сделана ради сопоставимости годов на длинной дистанции, а не ради текущей цифры. ⚠ Исключение действует ТОЛЬКО в базе карточки (`_isOpenBal` в `_chanOf`) и в поиске последнего месяца с поступлениями; на свод, сальдо и KPI Банка оно НЕ распространяется - там остаток остаётся поступлением. Пометки о пересчёте 2024 на карточке нет сознательно: в интерфейсе 2024 не показывается. ⚠ **Канал «прочие расчёты» сейчас ПУСТ, и это нормальное состояние - строка остаётся сторожем.** Единственный счёт, который в нём был («Задолженность по страховым взносам», 58 372,80 = два ввода остатка от 31.03.2024 на 50 258,10 плюс взаимозачёт 8 114,70 от 15.05.2026), разошёлся: остатки ушли из базы по правилу выше, взаимозачёт переехал в наличные через `BANK_ACC_CHANNEL_FIX`. Непустой канал означает «завели счёт, которого нет ни в шаблонах, ни в списке» - смотри предупреждение в консоли.
- **Банк, канал счёта - одна функция `bankAccChannel(name,fns)`**, не размазывать разбор имени по коду. ⚠ **Порядок: сначала ФНС, потом имя.** `fns===1` → `'da'` СРАЗУ: у р/с ООО и ИП канал по названию не определяется в принципе, при обратном порядке весь оформленный контур уехал бы в остаток. Дальше по имени: «карта ФЛ» → `'card'`, «касса» → `'cash'`, иначе `'unknown'`. ⚠ `'unknown'` = «по имени канал НЕ РАСПОЗНАН», а не «прочий вид счёта» - раньше значение звалось `'other'` и два смысла сливались. В подсказке строка называется **«прочие расчёты»** (не «прочее»): там реальный контур с ФНС=Нет, и он ВХОДИТ в базу расчёта. ⚠ Классификация по названию ХРУПКАЯ - заведут «Касса Иванова» и она молча уедет в наличные; поэтому каждое новое имя в `'unknown'` один раз пишется в `console.warn` («в справочнике появился вид счёта без правила»). Правильное решение на будущее - отдельный столбец-признак канала в источнике. ⚠ Регекс кириллицы - `[а-яё]`, а НЕ `\w`: `\w` в JS без флага `u` кириллицу не матчит, и «Карта ФЛ» уезжала в `'unknown'`. **Счета, не подпадающие под шаблоны имён, ведутся ЯВНЫМ списком `BANK_ACC_CHANNEL_FIX` в той же функции** - разносить список и шаблоны по разным местам нельзя, это одно правило. Ключ - имя в нижнем регистре со схлопнутыми пробелами, совпадение ПОЛНОЕ (подстрока молча захватила бы однокоренные счета). ФНС=Да списком не перебивается: налоговое оформление - другая ось, чем вид счёта. Первая запись: «Задолженность по страховым взносам» → наличные. Это обычная касса наравне с картами ФЛ и займами сотрудникам: по ней видно долг сотрудника на конец месяца и через неё идут взаимозачёты (поступление 8 114,70 от 15.05.2026 - реальный взаимозачёт). Предупреждение в консоли теперь означает «счёта нет НИ в шаблонах, НИ в списке».
- ⚠ **ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: в `RAW` НЕТ признака вида счёта.** 15 колонок (`DATE_DDS, DATE_OPIU, TYPE, OFFER_ID, INCOME, OUTCOME, FNS, ACCOUNT, ARTICLE_CODE, ARTICLE_NAME, ANALYTICS, SECOND_SIDE, PURPOSE, ACTIVITY_DIR, FIN_OP`) - вида счёта среди них нет, поэтому канал УГАДЫВАЕТСЯ по названию. Это уже стрельнуло дважды: «Карта ФЛ» не матчилась из-за `\w` и кириллицы, «Задолженность по страховым взносам» уехала в «прочие расчёты». Явный список - заплатка, а не решение. **План устранения**: добавить в источник колонку «Вид счёта», заполняемую из справочника выпадающим списком (как заполняются сами счета), и классифицировать по ней; шаблоны и список тогда уходят. До этого каждый новый счёт с непривычным названием будет молча попадать в «прочие расчёты» - следить за предупреждением в консоли.
- **Банк, ширины колонок свода**: классами `col.c-name`/`col.c-num`, НЕ инлайном - инлайн не перекрыть медиа-запросом. По умолчанию проценты (Σ = 24 + 4×19 = 100.0), на экране от 1600px - `c-num:128px` + `c-name:auto` (иначе на широкой карточке 19% дают 158px при нужных 121px и слева от каждого числа зияет ~55px). 128, а не 120: замер по самому длинному ПОДЫТОГУ («-118 382 486,10» = 121px), строки счетов короче. ⚠ **`width:min(19%,120px)` в `<col>` НЕ РАБОТАЕТ**: при `table-layout:fixed` Chrome игнорирует math-функции в ширине колонки ЦЕЛИКОМ и раскладывает все колонки поровну (замерено: 165/165/165/165/165 вместо 345/120/120/120/120). Допустимы только длина или процент - `calc()` работает, `min()`/`max()` нет. На ПЕЧАТИ свод переводится в ОДНУ колонку (`bank-cols{grid-template-columns:1fr}`): рядом на A4 карточке достаётся ~530px и пять колонок не помещаются.
- **Банк, клик по строке счёта - НЕ то же, что фильтр «Реквизиты счёта».** Клик пишет в `_bankFilter` и меняет ТОЛЬКО графики, свод остаётся целым и строка подсвечивается - по нему можно щёлкать дальше. Выпадающий список пишет в `_tabFilters.bank.accounts` и режет весь отчёт. Пробовали слить оба пути в один (`renderBank`) - ОТКАЧЕНО: свод схлопывался до одной строки и кликать становилось не по чему. ⚠ Дневной график строит ОТДЕЛЬНАЯ `bankUpdateDays`, и она обязана применять `_bankFilter.accs` тем же вторым шагом, что и месячный, а `bankRebuildChartData` - звать её: иначе клик по счёту менял месячный график, а дневной оставался на полных данных.
- **Банк, фильтр «ФНС» режет СЧЕТА по их признаку, а НЕ строки.** Признак счёта собирается из его строк (первое распознанное «да»/«нет» выигрывает, ни одного → `-1` «без признака»), значения `''`/`da`/`net`/`unk` (`BANK_FNS_OPTS` - один источник для фильтр-бара и поля пресета). Суммы внутри счёта от фильтра НЕ зависят, меняется только состав видимых счетов - поэтому числа остаются подмножеством несфильтрованного свода. Фильтруй он строки, счёт со смешанными строками менял бы итог и мог переехать в другую карточку, а свод перестал бы биться с общим. До этой правки фильтра по ФНС не существовало вовсе - признак только раскладывал счета по трём карточкам.
- **Пресеты Банка** (`PRESET_FIELDS.bank`): Название · Период · Направление · Реквизиты счёта · ФНС · Будущие оплаты. Список счетов - из `RAW` (`_presetAvailAccounts`), как «Направление»: пресет описывается независимо от текущих фильтров вкладки. Механика поля - как у фильтра на вкладке (переиспользован `bankDDFilter`; «выбрать все» берёт ВСЕ пункты, а не только видимые поиском - как `_bankExtraSelectAll`). ⚠ **Имена счетов содержат «/» (`S7 - Касса (№QY74954/CL)`, `р/с`) и обязаны лежать ЗНАЧЕНИЯМИ массива, а не ключами объекта** - ключом это уронило бы запись всей ветки `config/presets` в RTDB (та же ловушка, что была с `planOwners`). ⚠ `data-str="1"` на мультиполе счетов: без него счёт из одних цифр приводился бы к `Number` в `_presetSave` и переставал совпадать со строкой фильтра. Применение отдельного кода не требует - `presetApply` копирует ключи `p.f` в `_tabFilters[tab]`, а `renderBank` уже режет по `f.accounts`/`f.fns`.

## Модель БФЛ (вкладка bflmodel)

Параметрическая сценарная юнит-модель («к чему стремиться»), НЕ путать с вкладкой «Юнит-экономика» (marketing). Детали структуры — в коде и в ТЗ (`ТЗ_Юнит-экономика_БФЛ`, `ТЗ_ClaudeCode_БФЛ`). Ключевое:
- **Эталон ТЗ §6 содержит 2 несоответствия** (разобраны, не «чинить»): (1) §5.4 «ОС Расходы 3 306 194» — опечатка, из строк выходит 3 036 194; (2) депозит pass-through по числу эталона фактически НЕ вычитается (асимметрия в самом ТЗ). Модель по умолчанию **включает депозит** (как эталон); тумблер даёт net-вариант.
- Накладные (аренда/коммуналка/эквайринг) убраны из всех отделов по просьбе — только ФОТ + прямые затраты. Из-за этого ЦКП отделов отличаются от эталона §5; тесты `bflRunTests()` проверяют маркетинг (2700) и выручку точно, расходы — диапазоном.
- ФОТ ОМ входит в расходы маркетинга («моделируем правильно»). Контур ОПАУ — самоокупаемый, со своим ОПИУ, исключён из общего `bflOPIU`.
- **Авто-сохранение** при каждой правке в `config/bflModel` + localStorage; Firebase-listener применяет облако только если `savedAt` не старше локального (иначе затирал бы свежие правки).
