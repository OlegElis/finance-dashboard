# Finance Dashboard — правила проекта

> Дашборд управленческого учёта для ГК ОПОРА. Один файл `index.html` (весь HTML/CSS/JS,
> без фреймворков и сборщиков), хостинг GitHub Pages. Данные — Google Sheets API (read-only,
> API-ключ), лист `RawData`. Устройство вкладок, имена функций, поля состояния и структуру
> данных смотри в коде — здесь только то, чего в коде нет: договорённости, запреты,
> нестандартные решения и причины их принятия.

## Общие правила

- **Автопуш**: всегда пушить в GitHub автоматически после каждого коммита, без вопросов.
- **Дефис, не тире**: нигде не использовать «—», только «-» (в коде, UI и в чате).
- **Фильтры per-tab**: у каждой вкладки свои фильтры (`_tabFilters[tab]`). Изменение фильтров на одной вкладке НЕ влияет на другие.
- **Изоляция вкладок**: работая с одной вкладкой, НЕ трогать код других. У каждой вкладки есть набор «защищённых» функций (`renderBank`, `bankFillTxn`, `renderBflModel` и т.д.) — не менять их при работе над чужой вкладкой.
- **Локальная проверка перед пушем**: дашборд нельзя открывать через `file://` - Firebase Auth не работает вне http/https. Поднимать локально: `python -m http.server 8000` в папке проекта, открывать `http://localhost:8000`. В Google Cloud Console → API-ключ → HTTP referrers должен быть разрешён `http://localhost:8000/*` (уже добавлен).

## Данные и источник

- Google Sheets API, `valueRenderOption=UNFORMATTED_VALUE&dateTimeRenderOption=SERIAL_NUMBER`. **Даты приходят Excel-серийными числами** → `parseDate` конвертирует. Первая строка `RawData` — заголовки; индексы колонок фиксированы (`COL` в коде), перестановка колонок молча ломает отчёты.
- **Данные собираются через IMPORTRANGE** из источников. Во время пересчёта импорта шапка временно приходит пустой / `#ERROR!` / `Loading…` — поэтому сверка структуры листа (`connectAndLoad`, эталон в localStorage `fin_rawHeaders_{sheet}`) идёт ТОЛЬКО по «полной валидной» шапке (15 непустых, без `#`/`loading`), иначе была бы ложная тревога.
- Архивирование: данные тянутся через отдельный Apps Script (замороженный XLSX у источника); настройки бэкапятся кнопкой в дашборде.
- **Листы-справочники**: `RawData_BFL` — только БФЛ; `RawData_ID_Offer` — сделки ВСЕХ направлений (для сверки `ID_Offer` в Аномалиях/Депозитах). Матчить сделки **по системному ID** (число до «|»), а не по полному `ID_Offer`/ФИО/№ договора — их могут изменить, ID нет. Нормализация ID — `_arNormId`.

## Дизайн-система

- Все цвета/шрифты — CSS-токенами в `:root`, **не хардкодить hex** в компонентах (точные значения — в коде). Стиль: спокойный, плотный, данные-первичны.
- **Цвет = знак значения**: доход/прибыль зелёный (`--income`), расход/убыток красный (`--outcome`), остаток ДС оранжевый. Заголовки секций — нейтральный `--text2`, НЕ акцент.
- Бренд-акцент — графитово-синий `--accent` (был фиолетовый `#7c4ddb`, заменён по просьбе). Только для активной навигации/чекбоксов/логотипа/линий графиков, не для декора.
- Шрифты: IBM Plex Sans (интерфейс) + IBM Plex Mono с `tabular-nums` для ВСЕХ чисел. В `.report-table` 1-я колонка — текстовый лейбл (sans), остальные — числа (mono).
- Chart.defaults — mono, оси серые. Маркетинговая палитра завязана на легенды-чипы — не трогать без синхронизации легенды и графика.

## Безопасность (по аудиту)

- **`_htmlEsc(v)`** — ЕДИНСТВЕННЫЙ способ вставлять данные из Sheets (ячейки RAW) в `innerHTML`/`onclick`. Без него — хранимый XSS через ячейку. Применять во ВСЕХ новых рендерах для любых данных-лейблов.
- **CSV-экспорт** (`registryExportAI`): текст, начинающийся с `= + @ -` или таба, префиксовать апострофом (защита от формульных инъекций в Excel).
- **`_isAdmin()`** = текущий пользователь == `ADMIN_EMAIL` (`o017ev@gmail.com`). Гейтит запись общих `config/*` и админ-UI. Реквизиты `config/sheets` пишет ТОЛЬКО админ, сотрудники читают — иначе при правиле «запись = админ» каждый вход сотрудника ловил бы отказ. Попап лимитов реквизитов для не-админа — только просмотр.
- ⚠ Остаётся по дизайну: **Sheets API-ключ в исходнике** (нужно ограничение по referrer в Google Cloud Console). Клиентская модель доступа — **барьер от посторонних, а не строгая изоляция** (продвинутый юзер может запросить чужую вкладку; строгий вариант — Apps Script-прокси).

## Надёжность (по аудиту)

- **`_fbSetSafe(path,val,label)`** — ЕДИНСТВЕННЫЙ способ писать в `config/*`: при отказе правил БД/офлайне показывает alert «сохранено только локально». Раньше сейвы были fire-and-forget — «✓ Сохранено» врало, планы терялись при следующей загрузке.
- Каждый рендерер обёрнут в try/catch (`renderActiveTab`) — упавший показывает заглушку с текстом ошибки, а не мёртвую вкладку.
- **Logout обязан сбрасывать сессию**: `appLogout` гасит презенс и обнуляет `_appBooted`/`_dataSheet`, чтобы следующий вход перегрузил данные СВОЕЙ вкладки. Раньше новый пользователь видел RAW предыдущего. `watchForceLogout` сравнивает с `_flAuthMs` (обновляется на каждом входе), а не с `auth_time` первого входа.
- **MutationObserver-ловушка**: мобильные хелперы (`watchMobileCards`) и переинжект пресетов (`_setupPresetObserver`) слушают `#mainContent` и срабатывают на каждый ре-рендер. ⚠ Их колбэки НЕ должны безусловно мутировать DOM (писать `innerHTML` только при реальном изменении; сводку фильтров обновлять по data-sig) — иначе observer зацикливается.
- **Именные ловушки при правке кода**: имя `applyPreset` занято дат-чипами фильтр-бара — пользовательские пресеты называются `presetApply` (не путать). Глобального `esc` нет (он локален в каждой render-функции) — для эскейпа вне рендера свои хелперы (`_pesc`, `_htmlEsc`, `_dEsc`).
- **RTDB превращает числовые ключи в МАССИВ.** `config/plansBaseline/<year>/<month>` Firebase может сохранить как `{1:{...}}` или как `[null,{...}]` - зависит от плотности ключей. Читатели (`_baselineMonthsMap`) должны быть толерантны к обеим формам: `Object.keys()` работает и там, и там, но проверка `Array.isArray()` с ранним выходом отбрасывает валидные данные. При записи нормализовать к плоскому объекту (иначе форма-массив затирается на `{}` и теряет уже сохранённые ключи).

## Авторизация и доступ (Firebase Auth, email+пароль + Google)

- Дашборд закрыт экраном входа. Пользователи email/пароля заводятся **в консоли Firebase**, не в коде.
- **Белый список** (`checkAllowed`): доступ если email == `ADMIN_EMAIL` ИЛИ в `config/allowedEmails`. Применяется ко всем способам входа; не прошёл → авто-`signOut`.
- **Доступ по ролям (вариант A)**: `resolveAccess` → админ видит `RawData`; email в `config/sheetAccess` → свою вкладку; в `allowedEmails` → `RawData`. Это разрез «у каждого свой отчёт», НЕ строгая изоляция (таблица/ключ общие).
- **fail-open**: если Firebase/CDN недоступны или нет ключей — дашборд открывается без входа (барьер, а не защита; данные и так тянутся по API-ключу из исходников).
- **Рубильник «Сбросить сессии»** (админу): пишет `config/forceLogoutAfter`, каждая сессия слушает и делает `signOut`, если метка новее её `auth_time`.
- ЦФО/ответственные = люди с доступом: список ФИО берётся из `config/names` (отдельной панели ЦФО нет - объединена с «Управление доступом» по просьбе «все, кому дан доступ, должны быть ЦФО»).
- **Иерархия ЦФО (2 уровня)**: `config/cfoHierarchy = { "<ФИО подчинённого>":"<ФИО руководителя>" }`, один уровень вложенности; руководитель без записи = верхний уровень. Задаётся колонкой «Руководитель» в панели «Доступ», пишется через `_fbSetSafe` (`_cfoHierSave`), кэш localStorage + `startCfoHierarchySync`. Ключи по ФИО (как `_planOwners`) - при переименовании ФИО в панели записи `cfoHierarchy` И `planOwners` мигрируют на новое ФИО (`accessSavePanel`, матч по email). Ключ ответственности `_planOwners[dir||подстатья]` НЕ меняется. Свод ЦФО (`cfoHtml`) двухуровневый: строка руководителя = свои подстатьи + сумма подчинённых, раскрывается (`cfoToggleMgr`, чистый DOM-тоггл - не ре-рендер, чтобы `<details>` свода не схлопывался); ИТОГО считается по СЫРЫМ `agg` (листовым), поэтому факт ИТОГО не меняется от иерархии. Выписка (`cfoStatementGen`): для руководителя галочка «Включить подчинённых» → секции по людям («Свои подстатьи», затем каждый подчинённый) + ИТОГО по блоку; жёсткий фильтр по владельцу сохранён (подчинённый не видит чужих подстатей). Защита от цикла А→Б→А: `_cfoMgrOf`/`_cfoSubsOf` игнорируют самоссылку, дерево - строго один уровень.

### Правила RTDB (Firebase Console) — задаются вне кода, без них молча ломается
- `config/.read` = `auth != null`. Запись КАЖДОЙ ветки `config/*` = только `ADMIN_EMAIL` по `auth.token.email`: `plans, plansBaseline, allowedEmails, sheetAccess, names, planOwners, planNotes, rentObjects, targetLocked, presets, kassaLimits, sheets, forceLogoutAfter, bflModel, cfoHierarchy`.
- `presence` / `activity/$ek` = `auth != null` (per-user).
- ⚠ Ветка без правила записи → сохранение молча запрещается. Особенно важно для `config/bflModel` (модель БФЛ) и планов.

## Ключевые учётные решения (иначе выглядят как баг и будут «исправлены» обратно)

- **`120_Ввод начального остатка` — НЕ выручка НИГДЕ** (глобальный хелпер `isOpeningBalance`, единообразно в ОПиУ/БДР/ФОТ/Структуре/Юнит-экономике). Это входящий остаток, а не доход; раньше раздувал ЧП и завышал %-планы. Прочие `120_` (реализация имущества, депозит, возмещение) — выручка. **ОПиУ и БДР считают выручку одинаково.**
- **«Вывод чистой прибыли» (код 127, дивиденды) НЕ входит в расходы и в ЧП** — вынесен в отдельную секцию «Распределение прибыли» ниже линии ЧП (в ОПиУ, БДР, Структуре расходов). Иначе ЧП расходилась с ОПиУ ровно на сумму дивидендов.
- **Проверка после любой правки расчётов БДР (сверка, НЕ константа)**: «ИТОГО РАСХОДЫ факт» в БДР должно совпадать с «РАСХОДЫ» в ОПиУ за тот же период и то же направление. Обе цифры считаются из одного `RAW` разными путями — совпадение доказывает, что расчёт не сломан. Конкретное значение постоянно меняется по мере пополнения базы транзакций, поэтому проверяется РАВЕНСТВО двух отчётов, а не совпадение с фиксированным числом (прежняя контрольная константа устарела и удалена). ⚠ Осторожно: `127_вывод прибыли` в ОПиУ вынесен ниже ЧП, в БДР — в секцию «Распределение прибыли»; сравнивать расходы БЕЗ вывода 127.
- **Расчётный транзит почты БФЛ↔САУ** (ОПиУ, чекбокс): виртуальные строки (в Sheets НЕ пишутся), только когда выбран ровно один контур. Кейс: БФЛ + `112_Депозиты и госпошлины` + |списание| ∈ {25000,50000} + непустой `ID_Offer` → транзит **фикс 20000 ₽/ID** (плейсхолдер; при факте заменить на фактические суммы). БФЛ −20000, САУ +20000.
- **EBITDA-корректировки** — непрофильные/разовые расходы; значение аналитики в Sheets должно быть ровно `EBITDA-корректировки`. Тумблер двигает их выше/ниже EBITDA; ЧП в обоих режимах одинакова.
- **Займы сотрудникам — знаковая модель**: `amount = inc + out`; `>0` выдача, `<0` возврат; долг = Σ amount. Нельзя брать возврат как `abs(поступления)` — иначе выдача (+) и возврат (−) оба считаются возвратом и долг задваивается.
- **Календарный `daysB`** (разница `Date.UTC` по локальным компонентам) — в Займах, Дебиторке, Депозитах. Прямое `(b-a)/сутки` занижало на 1 день и давало «−1 дн.» для операций «сегодня».
- **БДР: baseline (`config/plansBaseline`) - замороженный утверждённый план года. Не редактируется никогда.** Прогноз (`config/plans`) правится свободно, baseline - только через «Утвердить план года» (снимок прогноза, только админ, только при сохранённом плане - иначе staged-правки откатились бы по «Отмена», а baseline остался бы с ними). Отклонения (Δ) и KPI «Исполнение YTD» считаются ОТ baseline; «Прогноз года · ЧП» - от прогноза. Причина: план, который можно править задним числом, делает отклонение недоказуемым. %-планы baseline конвертируются в рубли от СВОЕЙ (снимковой) базы выручки (`buildPlanCalc` со своей income-базой), а не от текущего прогноза - иначе замороженный процент поплывёт; `_planIncBaseMonth` (база прогноза) при этом не трогается. Наборы строк (`codeSet`/`incSet`/`vyvodSet`) пополняются кодами из baseline: иначе статью можно спрятать, убрав её из прогноза. UI: 3 колонки «Утверждено | Прогноз | Факт | Δ к утв.»; без baseline колонка пуста, Δ не считается, красный баннер «план не утверждён». Печать (`planPrintOwners`) остаётся прогнозной + штамп об утверждении. **Флаг `retro` (ретроспектива)**: месяц заморожен, но НЕ планировался заранее (план проставлен задним числом = факт; чекбокс при заморозке, поле `retro` в объекте месяца, отсутствие → false). retro-месяцы ИСКЛЮЧАЮТСЯ из «Исполнение YTD · расходы/доходы» (`_planableFrozenMonths`), иначе дают фальшивые ~100%; но ОСТАЮТСЯ в «Утверждено»/Δ/остатке лимита/коридоре графика (цифры верны). Все замороженные = retro → карточки YTD прочерк «нет планируемых месяцев». Пометка 📋 (вместо ⚠) в матрице и выписке ЦФО.
- **БДР, режим «Статья»: строка-статья группируется по c3 подстатьи (`ARTICLE_NAME`), а не по коду статьи.** Причина двойная: (1) разные статьи бывают с одинаковым c3 (`111_ФОТ` и `111_ФОТ (выслуга лет)`) — при группировке по полному `ARTICLE_CODE` `planAgg(c3)` отдавал план всей группы каждой статье, и план в ИТОГО задваивался; (2) ключ берётся от подстатьи, а не от статьи, потому что разворот (`subsOfArt`/`factSubN`) группирует детей по их c3 — иначе на строках с расхождением c3 статьи и подстатьи (ловятся в Аномалиях) статья ≠ Σ подстатей. Пустая подстатья даёт дочернюю строку под кодом статьи (`sn=an||ac`), чтобы не теряться молча. Лейбл строки = «c3 · представитель» (`ARTICLE_CODE` с макс. оборотом в группе). Фильтр по статье работает по c3: выбор одного полного кода тянет всю c3-группу.

## Решения пользователя по вкладкам (не откатывать)

- **Юнит-экономика (marketing)**: CPL скрыт (логика в коде сохранена); `112_Распределение КМ` и `112_Транспортные` в CPF не включаются; подстатей `300_Реклама/маркетинг` и `244_Контроль качества` в данных НЕ существует. Направление — одиночный выбор, «Все направления» нет. Для БФЛ количества считаются авто из `RawData_BFL`; тех-специалисты (`EXCL_RESP_*`, по «Кем создана сделка») исключаются из количеств, но остаются в дебиторке.
- **Аномалии**: только жёсткие детерминированные правила (массив `RULES`), без статистики — статистика давала много шума. В правиле «карты АУ/САУ» (`aucard`) карта **СберБанк-1638 Елисеев ИСКЛЮЧЕНА** из `AU_CARDS` — она используется в любых направлениях, а не только АУ/САУ.
- **Дубли**: сравнение ВСЕЙ строки целиком после trim, без исключений. Удаление — только вручную в Sheets (дашборд read-only).
- **Дебиторка БФЛ**: оплата (нетто) = поступления − только `112_Возвраты клиентам`; депозит суда (`120_Поступление депозита`) и перемещения оплатой НЕ считаются. Закрытые стадии ВКЛЮЧЕНЫ по умолчанию (по ним мог остаться долг). Сделки до 01.04.2024 скрыты по умолчанию (старая дебиторка фиктивная).
- **Займы**: определяются по «Реквизиты счёта» содержащему «займ»+«сотрудник»; статья/подстатья не участвуют.
- **Депозиты АУ**: вывод (127) больше не отслеживается — после возврата поток идёт в операционные расходы АУ/САУ.
- **ФОТ / Структура расходов**: «Вывод прибыли» исключён из расходов (иначе итог расходится с ОПиУ).
- **БДР (planfact), раскладка**: на десктопе (>820px) вкладка - флекс-стек фиксированной высоты (`#tabPlanfact`, CSS-блок в head): скроллится ТОЛЬКО `.table-scroll`, фильтр-бар/KPI/заголовок/sticky-шапка стоят. У таблиц `border-collapse:separate` - НЕ возвращать `collapse` (sticky-шапка в таблицах с collapse глючит в браузерах; это и было причиной «уезжающей шапки»). Графики - `<details id="pfCharts">`, свёрнуты по умолчанию, состояние в `_tabFilters.planfact.chartsOpen`, после разворота `pfChartsResize` (чарты создаются при display:none). Мобила и печать - обычный поток (@media).
- **Редактор планов, «⤓ заполнить фактом»**: маркер «план ≠ факт» (подпись «факт X» + янтарная рамка) ставится ТОЛЬКО при ненулевом факте - будущие месяцы без «факт 0,00» под каждой ячейкой (это был оранжевый шум). Маркер - тонкая рамка + бледный фон, не насыщенная заливка. `borderColor` входит в снимки undo (⤓/⌫/↶) - при правке снимков не терять. Строки, где нет ни плана, ни факта - `plan-row-empty` (приглушены opacity, оживают hover/focus, НЕ скрыты).

## Ловушки по вкладкам (корректность/UX — не «упрощать»)

- **ОСВ, переходящее сальдо**: скрытые периоды ДО первого видимого вкатываются в «Сальдо нач.» ТОЛЬКО в `rowCalc`; цикл `buildRow` стартует с `lastVisIdx = pksAll.indexOf(visPks[0]) − 1` и докатывает лишь скрытые периоды МЕЖДУ видимыми. Иначе при обрезке разреза «день» (лимит 62 дня) получается двойной счёт сальдо.
- **Банк, extra-фильтры**: списки значений в дропдаунах строятся из `dataBase` (снимок ДО применения extra-фильтров), чтобы выбор одного значения не «схлопывал» список остальных.

## Модель БФЛ (вкладка bflmodel)

Параметрическая сценарная юнит-модель («к чему стремиться»), НЕ путать с вкладкой «Юнит-экономика» (marketing). Детали структуры — в коде и в ТЗ (`ТЗ_Юнит-экономика_БФЛ`, `ТЗ_ClaudeCode_БФЛ`). Ключевое:
- **Эталон ТЗ §6 содержит 2 несоответствия** (разобраны, не «чинить»): (1) §5.4 «ОС Расходы 3 306 194» — опечатка, из строк выходит 3 036 194; (2) депозит pass-through по числу эталона фактически НЕ вычитается (асимметрия в самом ТЗ). Модель по умолчанию **включает депозит** (как эталон); тумблер даёт net-вариант.
- Накладные (аренда/коммуналка/эквайринг) убраны из всех отделов по просьбе — только ФОТ + прямые затраты. Из-за этого ЦКП отделов отличаются от эталона §5; тесты `bflRunTests()` проверяют маркетинг (2700) и выручку точно, расходы — диапазоном.
- ФОТ ОМ входит в расходы маркетинга («моделируем правильно»). Контур ОПАУ — самоокупаемый, со своим ОПИУ, исключён из общего `bflOPIU`.
- **Авто-сохранение** при каждой правке в `config/bflModel` + localStorage; Firebase-listener применяет облако только если `savedAt` не старше локального (иначе затирал бы свежие правки).
