# Finance Dashboard — правила проекта

## Общие правила

- **Автопуш**: всегда пушить в GitHub автоматически после каждого коммита, без вопросов
- **Фильтры per-tab**: каждая вкладка имеет свои фильтры. Изменение фильтров на одной вкладке НЕ влияет на другие
- **Изоляция вкладок**: при работе с одной вкладкой НЕ трогать код других вкладок

---

## Архитектура

### Стек
- Один файл `index.html` — весь HTML, CSS, JS
- Без фреймворков и сборщиков
- Хостинг: GitHub Pages (или локально)

### Источник данных
- Google Sheets API (read-only, API Key)
- Лист `RawData`, первая строка — заголовки
- Запрос: `valueRenderOption=UNFORMATTED_VALUE&dateTimeRenderOption=SERIAL_NUMBER`
- Даты приходят как Excel-серийные числа → `parseDate` конвертирует
- Архитектура: один сводный лист, данные собираются через IMPORTRANGE из источников

### Структура данных (COL)
```js
COL = {
  DATE_DDS: 0, DATE_OPIU: 1, TYPE: 2, OFFER_ID: 3,
  INCOME: 4, OUTCOME: 5, FNS: 6, ACCOUNT: 7,
  ARTICLE_CODE: 8, ARTICLE_NAME: 9, ANALYTICS: 10,
  SECOND_SIDE: 11, PURPOSE: 12, ACTIVITY_DIR: 13, FIN_OP: 14
}
```

### Глобальное состояние
```js
RAW          // массив всех строк из Google Sheets
activeTab    // 'bank' | 'dds' | 'opiu' | 'osv' | 'fot' | 'planfact' | 'expenses' | 'marketing' | 'debtbfl' | 'dupes' | 'incomplete'
// Меню: Отчёты (БАНК, ДДС, ОПиУ, ОСВ, ФОТ, ПЛАН-ФАКТ) → Аналитика (Структура расходов, Маркетинг, Дебиторка БФЛ) → Контроль (Дубли, Недозаполненные) → Данные
// planfact — заглушка «в разработке» (renderPlanFact); заголовки: bank='Реестр банковских и кассовых операций (БАНК)' (в меню — «БАНК»), osv='Оборотно-сальдовая ведомость (ОСВ)' (в меню — «ОСВ»)
_tabFilters  // фильтры per-tab (dateFrom, dateTo, preset, periodType, activityDirs, ...)
_bankTxnFilter  // {accs, date} — фильтр таблицы операций (счёт/день)
_mktCounts   // {periodKey: {leads, orders, fulfilled}} — ручной ввод маркетинга, персистится в localStorage
```

### Паттерн рендера
Каждая вкладка — функция `renderXxx(f)`, где `f = getFilters()`. Функция полностью перестраивает innerHTML вкладки. Вызывается из `renderActiveTab()`.

## Вкладки

### 1. Банк и касса (`bank`)

#### Артефакты
1. **Фильтр-бар** — даты + пресеты + extra-bar с мультивыборами
2. **KPI-бар** — 4 карточки: Поступления / Списания / Сальдо / Счетов + Cash Runway
3. **Свод по счетам** — Денежные средства (ООО, ИП) + До налогового оформления (Карты ФЛ, Кассы ЦФО)
4. **Графики** — верхний (по годам/месяцам) + нижний (по дням, клик → фильтр)
5. **Таблица операций** — 22 строки, пагинация 500, клик на строку → модал карточки

#### Extra-фильтры (строка под основным фильтром)
Мультивыбор с чекбоксами: **Направление / ID Offer / Статья / Подстатья / Фин. операция / Контрагент**
- У всех дропдаунов (кроме Направления) есть **поле поиска** по значениям
- Применяются ко **всем блокам листа** (свод, KPI, графики, таблица). Применение — при закрытии дропдауна (полный `renderBank`)
- Списки значений в дропдаунах строятся из `dataBase` (до extra-фильтров), чтобы выбор не «схлопывал» список
- Кнопка `× сброс` сбрасывает все фильтры таблицы
- Поля состояния: `offerIds, articles, subarticles, finOps, secondSides` в `_tabFilters.bank`

#### Тумблер «Будущие оплаты» (`_tabFilters.bank.includeFuture`)
- вкл (по умолчанию) → добавляются плановые/будущие платежи с датой позже сегодня
- выкл → только операции по текущий день включительно (по `DATE_DDS`/`DATE_OPIU`)
- Применяется ко **всему листу Банк**: свод, KPI, графики, таблица операций

#### Лимиты реквизитов (KPI-карточка «Лимиты счетов»)
- Карточка в KPI-баре показывает статус: «Превышение: N» (красный) / «В норме» (зелёный) / «Не настроено» / «Нет счетов»
- Лимиты задаются для **всех именованных реквизитов**: счета ООО/ИП, Карты ФЛ, Кассы (исключая «без реквизитов»). Остаток = `total` счёта (с учётом фильтров)
- Клик → попап (широкий): таблица Тип / Реквизит / Остаток / Лимит (редактируемое поле) / Статус. Изменения применяются сразу
- Лимиты хранятся в **localStorage** (`kassaLimits` = `{accName: number}`), функции `_kassaLimits`, `_kassaSaveLimits`, `kassaSetLimit`, `showKassaLimitsPopup`
- При закрытии попапа — `renderBank` обновляет карточку. В планах: перенос лимитов в Google Sheets

#### Cash Runway
- Текущий баланс (saldo из отфильтрованных данных) ÷ средний операционный расход × 30
- Расходы: только FIN_OP начинается с `001_`, последние 90 дней до текущего месяца
- Клик на карточку → попап с детализацией по месяцам

### 2. ДДС (`dds`)
- Отчёт о движении денежных средств
- Использует `DATE_DDS`
- Extra-фильтры: **Год** (мультивыбор) / **Месяц** (мультивыбор) / **Направление** (мультивыбор) / **Период**
- Месяцы фильтруются по выбранным годам
- Секции: I Операционная / II Финансовая / III Инвестиционная / IV Прочее
- Исключаются строки с TYPE = «перемещение»

---

### 3. ОПиУ (`opiu`)
- Отчёт о прибылях и убытках (ОПиУ)
- Использует `DATE_OPIU`
- Extra-фильтры: **Год** (мультивыбор) / **Месяц** (мультивыбор) / **Направление** (мультивыбор) / **Период**
- Категории расходов берутся из колонки **АНАЛИТИКА** (`COL.ANALYTICS`). Массив `CATS`:
  `Прямые / Переменные`, `Прямые / Постоянные`, `Косвенные / Переменные`, `Косвенные / Постоянные`, `Налоги / проценты / амортизация`, `EBITDA-корректировки`, `Вывод чистой прибыли`
- Секции отчёта: ВЫРУЧКА → ПРОИЗВОДСТВЕННЫЕ РАСХОДЫ (Прямые) → КОСВЕННЫЕ РАСХОДЫ → EBITDA → РАСХОДЫ НИЖЕ EBITDA (налоги + EBITDA-корректировки) → ЧИСТАЯ ПРИБЫЛЬ → РАСПРЕДЕЛЕНИЕ (вывод прибыли)
- **EBITDA-корректировки** — непрофильные/разовые расходы (корпоратив, обучение собственника и т.п.). Значение аналитики в Google Sheets должно быть ровно `EBITDA-корректировки`
- **Тумблер «Включить EBITDA-корректировки в EBITDA»** (`_tabFilters.opiu.ebitdaInclBelow`):
  - выкл (по умолчанию) → корректировки идут ниже EBITDA, на сам EBITDA не влияют
  - вкл → корректировки в составе косвенных расходов, уменьшают EBITDA
  - чистая прибыль одинакова в обоих режимах (меняется только позиция относительно линии EBITDA)
- В **ДДС** аналитика не используется: классификация по `FIN_OP` (`001_/002_/003_/other`). EBITDA-корректировки попадают в раздел по своему `FIN_OP`, а не по аналитике

### 4. ФОТ (`fot`)
- Фонд оплаты труда
- Считается **строго по дате ОПиУ** (`DATE_OPIU`, начисление); строки без ОПиУ-даты исключаются
- Статьи: префиксы `FOT_PREFIXES` (111_/226_/127_), только списания
- Фильтр-бар — **одна строка, без пресетов** (собственный бар ФОТ, не `renderFilterBar`): даты / Период / Детализация / **Статья / Подстатья / Сотрудник (контрагент)** — мультивыбор с поиском (можно посмотреть ФОТ одного человека). Состояние: `articles, subarticles, counterparties` в `_tabFilters.fot`
- Детализация: по направлению / подстатье / контрагенту
- Визуализация: накопительный график динамики по группам + горизонтальный рейтинг топ-групп + KPI динамики; в таблице доли в %

### 5. Маркетинг (`marketing`)
- Метрики: **CPMT** (Cost Per Meeting, стоимость встречи), **CPO** (стоимость сделки), **CPF** (стоимость исполнения) + **Конверсия встреча→сделка** — верхнеуровневые. CPL скрыт по решению пользователя (логика/списки в коде сохранены — не показывается в KPI и таблице)
- **Варианты «по ФОТ»** (`meetFot`/`cpoFot`): те же знаменатели (встречи/сделки), но в расходах — **только зарплаты воронки 111_*** (`costs.cpoFot` = строки CPO, у которых подстатья начинается с `111_`; `costs.meetFot=costs.cpoFot`). Без рекламы 300_* и 226_. Показываются и в KPI, и в таблице рядом с полными CPMT/CPO; полные (по всей воронке) метрики сохранены. Расшифровка `mktShowCostModal('meetFot')` мапит на `cpoFot`
- **CPMT — стоимость встречи** (внутренний ключ метрики `meet`): использует **те же расходы воронки, что и CPO** (`costs.meet=costs.cpo`), делённые на число встреч. Встреча = «Дата создания сделки» (`RawData_BFL`, массив `meetings`, ⚡ авто для БФЛ). Связь метрик: **CPO = CPMT ÷ конверсия(встреча→сделка)**. Расшифровка расходов CPMT = расшифровка CPO (`mktShowCostModal('meet',…)` мапит на `cpo`). На графике CPMT и CPO — **две линии на одном холсте** (`mktChartCpo`, с легендой); CPF — отдельный холст
- KPI-карточки: под значением — строка динамики, сравнивающая **два последних ЗАПОЛНЕННЫХ периода** (где метрика считается), напр. «↑ 300% Февраль 2026 к Январь 2026»; пустые будущие месяцы со случайным расходом игнорируются (фильтр `periods.filter(metricAt!=null)`)
- **Конверсия встреча→сделка** = кол-во сделок ÷ кол-во встреч (выше = лучше, рост зелёный). Отдельная KPI-карточка + строка «Конверсия воронки» в таблице (ячейки `mkt-conv-{pk}`)
- Расходы берутся из RAW по подстатьям (ARTICLE_NAME), матчинг `mktMatch` = точный список `MKT_SUBART` + префиксы `MKT_PREFIX`:
  - CPL: `111_Заработная плата АО`, `111_Заработная плата ОМ` + **все `300_*`** (Лидогенарация, Акция Приведи друга, Выплата Агентам, Дизайн и полиграфия, Медиаразмещение, Маркетинг прочее)
  - CPO: `111_Заработная плата АО/КО/КО2/ОМ/ОП`, `226_Контроль качества` + **все `300_*`**
  - CPF: `111_Заработная плата АУ/ОИ/ОС` + фиксированный список `112_*` (адвокатский запрет, возвраты, депозиты, СРО, почтовые, прочие платежи, публикации, торги, экспертиза)
  - ⚠ Подстатей «300_Реклама / маркетинг» и «244_Контроль качества» в данных НЕ существует — не возвращать
- **Направления не смешиваются**: фильтр «Направление» — одиночный выбор (`activityDir`), опции «Все направления» НЕТ; по умолчанию `БФЛ - Банкротство физических лиц`; расходы фильтруются строго по выбранному
- `112_Распределение КМ` и `112_Траспортные расходы` в CPF **не включаются** (решение пользователя)
- Фильтры в стиле ОПиУ: **Год** (мультивыбор) / **Месяц** (мультивыбор) / **Направление** (одиночный) / **Период** (разрез). Пресетов и выбора дат нет. По умолчанию — текущий год, разрез помесячно
- График динамики CPO/CPF: при выбросе (>3× медианы) шкала Y ограничивается ~медиана×2.5 — иначе всё «сплющивается» в полосу. **У каждой точки подписано значение** (плагин `valueLabels`, формат К/М); на графике CPMT+CPO 1-я линия подписана сверху, 2-я снизу (чтобы не накладывались). Пиковые значения, выходящие за шкалу, подписываются числом над графиком (`▲ N`)
- Знаменатели (кол-во лидов/сделок/дел) — **ручной ввод** по периодам, **отдельно для каждого направления**
- **Для направления БФЛ** все количества считаются **автоматически** из листа Google Sheets `RawData_BFL` (`loadBflDeals` → `RAW_BFL={leads,meetings,paid,done,deals}`):
  - лид = «Дата создания Лида»; **встреча = «Дата создания сделки»** (массив `meetings`); сделка = «Дата входа в стадию "Полная/частичная оплата"»
  - исполнено (CPF) = «Дата завершения сделки», **только** для стадий `Производство. Акты подписаны, работы завершены` и `Отдел сопровождения. Акты подписаны` (массив `DONE_STAGES`)
  - «Дата создания сделки» = **встреча** (используется в метрике СВ и конверсии встреча→сделка)
  - **Тех. специалисты исключаются из статистики количеств** (лиды/встречи/сделки/завершения) по полю **«Кем создана сделка (текст)»** (`iCreatedBy`, не «Ответственный»): `EXCL_RESP_EXACT` (точное совпадение: Павличенко Елизавета Сергеевна, Шелков Александр Сергеевич) + `EXCL_RESP_PREFIX` (по префиксу: Гагарина Варвара). В `deals[]` (дебиторка) такие строки **остаются** — исключение только из количеств метрик
  - Поля помечены «⚡ авто», ручной ввод для них скрыт. Лист не критичен: при его отсутствии — ручной ввод
  - **Количества кликабельны (⚡ авто)**: клик по ячейке кол-ва встреч/сделок/завершений/лидов → модал `mktShowCountModal(field,pk,label)` со списком записей (дата/ФИО/ID_Offer/№ договора/стадия/ссылка Bitrix24). Записи хранятся в `RAW_BFL.{leadsRows,meetingsRows,paidRows,doneRows}` (объекты `{date,fio,offer,contract,stage,responsible,url}`), раскладываются по периодам в `window._mktCntRows[field+'|'+pk]`. Для ручного ввода (не БФЛ) расшифровки нет
- В отчёт попадают **только периоды с маркетинговым расходом** (`mktMatch`), а не любые списания — будущие/посторонние месяцы не раздувают график. Подписи оси X сокращены («Янв '26»), полное имя периода — в тултипе; ось авто-прореживается
- Хранение ручного ввода: **localStorage** (`mktCounts` = `{dirKey:{periodKey:{leads,orders,fulfilled}}}`, dirKey=`__all__` для «Все направления»; старый плоский формат мигрируется автоматически)
- В планах: перенести хранение в Google Sheets (Apps Script Web App)

### 6. Структура расходов (`expenses`)
- Все расходы как в ОПиУ, но **без рентабельностей/EBITDA/прибыли** — только состав и веса
- По дате ОПиУ; группировка: **аналитика (категория) → подстатья**
- Колонки: **Сумма / Доля в расходах / % от выручки**; строка ИТОГО
- Фильтры: даты + пресеты + период + **Направление** (мультивыбор)
- Визуализация: **donut** долей категорий + горизонтальный **рейтинг топ-подстатей** (% от выручки в тултипе)
- KPI: Выручка / Расходы всего / Доля расходов в выручке / Категорий

### 7. ОСВ по счетам (`osv`)
- Оборотно-сальдовая ведомость по реквизитам (`renderOSV`), строго по `DATE_DDS`
- Сальдо на начало = записи подстатьи **«120_Ввод начального остатка»** (всегда, независимо от даты) + сумма всех операций до начала периода; обороты Дт (поступления) / Кт (списания) внутри периода (без записей ввода остатка); сальдо кон. = нач. + обороты
- Фильтры в стиле ДДС/ОПиУ: **Год** (мультивыбор) / **Месяц** (мультивыбор, зависит от годов) / **Счёт** (мультивыбор с поиском) / **Направление** / **Разрез**. Дат-инпутов нет
- Разрезы (`periodType`): `all` (4 колонки) / `year` / `month` / `day` — на каждый период четвёрка **Сальдо нач. / Дт / Кт / Сальдо кон.** (нач. периода = кон. предыдущего); день ограничен 62 днями
- Невыбранные месяцы внутри диапазона вливаются в переходящее сальдо (баланс сходится); в `all` — в «Сальдо нач.»
- Клик по строке счёта ничего не делает (выбор счёта — только через фильтр)
- Без группировки: все счета одним списком **по алфавиту** + строка ИТОГО; числовые колонки выровнены справа
- Закреплены при прокрутке: обе строки шапки (sticky top 0/30px) и левая колонка «Счёт / Реквизит» (sticky left)
- Отрицательное сальдо подсвечивается красным (индикатор ошибки в данных)
- Тумблер «Строки» (`rowDim`): `account` (по счетам, дефолт) / `direction` (по направлениям) — измерение строк таблицы; вынесен в **правый угол** фильтр-бара (`margin-left:auto`)
- Тумблер «Без вход. сальдо» (`noOpening`): выкл (дефолт) — сальдо с входящим остатком; вкл — сальдо считается с нуля, показывает только обороты выбранных периодов (без начального остатка и переходящего)
- Состояние: `years, months, accounts, activityDirs, periodType, rowDim` в `_tabFilters.osv`; dd-функции генерируются `_osvDD()`

### 8. Дебиторка БФЛ (`debtbfl`)
- Задолженность по договорам БФЛ (`renderDebtBfl`): **сумма договора** из листа `RawData_BFL` (колонка «Сумма»), **оплачено (нетто)** = Поступления − **только `112_Возвраты клиентам`** (прочие списания по ID — госпошлины/публикации и др. расходы дела — оплату НЕ уменьшают) из `RawData` **только с направлением `БФЛ - Банкротство физических лиц`**, связь по **ID_Offer**. В модале расшифровки показываются поступления + возвраты клиентам
- ID нормализуется `_arNormId` (NBSP→пробел, схлопывание пробелов, пробелы вокруг `|`) — перенос логики из старого Apps Script
- Долг = сумма договора − оплачено; только сделки с суммой > 0; дубли ID схлопываются (макс. сумма)
- **Переплата**: в колонке «Долг» показывается зелёным `+сумма` с подсветкой; ⚠ у %; тумблер-фильтр «⚠ Переплата (N)» (`overOnly`) — только переплаченные, сортировка по размеру переплаты
- **Давность оплат**: кол-во оплат / дата последней (по ДДС) / дней без оплат / категория `_arPayCategory` (до 30 / 31–60 / 61–90 / 91+ / Нет оплат) с цветным бейджем
- **«⚠ Нет в Bitrix24»** — тумблер-режим: оплаты по ID, отсутствующим в листе сделок (контроль расхождений). **Сверка по уникальному ID Bitrix24** (`_arLeadId` — первые цифры до «|», индекс `byLeadId`): если по полному ID_Offer сделки нет, но lead-id совпадает с существующей сделкой — в строке и модале показывается найденная запись Bitrix24 (ФИО/№ договора/сумма/стадия/менеджер/дата/ссылка) с пометкой «✓ найдено в Bitrix24 по ID»; если не найдено и по lead-id — «✗ нет даже по ID». Поля orphan-объекта: `isOrphan, bxMatch, leadId, bxSum`
- Первая колонка таблицы — **ID_Offer** (он уже содержит id | № договора | ФИО; колонок Клиент/№ договора нет). **Клик по ID** → модал `arShowDetail`: сумма договора, поступления/возвраты/нетто, формула долга + движения по ID **в формате всплывающего окна ДДС** (те же 15 колонок и стили TH/TD; клик по строке → `ddsShowRecordCard`; строки в `window._arMoves`); строки таблицы в `window._arRows`
- В режиме «Нет в Bitrix24» ID тоже виден и кликабелен — модал показывает предупреждение об отсутствии сделки и список оплат
- KPI: Сумма договоров / Оплачено нетто (%) / Дебиторка (%) / Договоров с долгом (+счётчик без сделки)
- Фильтры: поиск (debounce 300мс) / Стадия (мультивыбор+поиск) / Менеджер («Ответственный (текст)», мультивыбор+поиск, `_arDD`) / Давность оплаты (select) / «Только с долгом» (вкл по умолчанию)
- **Закрытые стадии ВКЛЮЧЕНЫ по умолчанию** — по ним мог остаться долг («перестал платить», недоплата при завершённых работах). Тумблер «Скрыть закрытые (N)» (`hideClosed`) убирает их (маркеры `AR_CLOSED_MARKERS`: работы завершены / перестал платить / расторг / брак / потерян / не отвечает / дорого и т.д.)
- **Переключатель «Сделки с апр 2024 (скрыто старых: N)»** (`cutoffOn`, вкл по умолчанию): скрывает сделки, созданные до 01.04.2024 (старт учёта оплат — у более старых дебиторка фиктивная); сделки без даты создания не отсекаются
- **KPI считаются по текущей выборке** — реагируют на ВСЕ фильтры (поиск, стадия, менеджер, давность, отсечка, закрытые и т.д.)
- Колонка **«Дата сделки»** после ID_Offer; клик по заголовку — сортировка по дате ▲/▼/сброс (`dateSort`, `arToggleDateSort`); по умолчанию сортировка по долгу
- Состояние: `search, onlyDebt, stages, resps, payCat, orphansOnly, hideClosed, overOnly, cutoffOn, dateSort` в `_tabFilters.debtbfl`
- Если `RAW_BFL` не загружен — заглушка с подсказкой переподключиться

## Группа «Контроль»

### 7. Дубли (`dupes`)
- Поиск **полных дублей** записей: совпадение **всех ячеек строки** (вся строка целиком, не только 15 известных колонок) после trim (`renderDupes`). Режим один — все ячейки, без исключений
- KPI: групп дублей / лишних строк / задвоено поступлений / задвоено списаний (лишние = все строки группы сверх первой)
- Таблица групп (макс 200) — точная копия таблицы «Операции» Банка (тот же `colgroup` c классами `c-*`, 15 колонок, `txn-table`); клик на строку → карточка операции (`dupesShowCard`, строки в `window._dupesRows`). Лишние строки выделены красным
- Кнопка **«Сформировать отчёт»** (`dupesPrintReport`) — открывает печатную версию (окно с автопечатью → печать или сохранение в PDF для бухгалтера). Данные в `window._dupesGroups`/`_dupesMeta`
- Удаление дублей — только вручную в Google Sheets (дашборд read-only)

### 8. Недозаполненные данные (`incomplete`)
- Проверка обязательности полей по регламенту заполнения (`renderIncomplete`)
- **Ошибки** (красные): пустые ДДС / ОПиУ / Тип / Статья / Подстатья / Направление / Фин. операция; нечисловые Поступление/Списание (0 — валидное значение); несовпадение первых 3 цифр кода Подстатьи и Статьи; **перемещение без пары** (перемещения группируются по дате ДДС + |сумме Поступления|: должна быть пара −X/+X с суммой 0; нулевое перемещение — тоже ошибка)
- **Предупреждения** (жёлтые, допустимая временная пустота): ФНС, Реквизиты счёта (заполняет фин.менеджер), Аналитика при типе «списание». ID Offer не проверяется
- KPI: строк с ошибками / только предупреждения / корректных / проверено. Чипы-разбивка нарушений по полям
- Таблица (лимит 500): колонка «Проблемы» + 15 колонок как в Банке, проблемные ячейки подсвечены; клик → карточка (`incShowCard` переиспользует `dupesShowCard`)
- Строки совсем без дат включаются в проверку независимо от дата-фильтра
- Фильтр по датам; группа в меню «Контроль» — сюда добавлять будущие проверки качества данных
