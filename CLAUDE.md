# Finance Dashboard - правила проекта

## Общие правила

- **Автопуш**: всегда пушить в GitHub автоматически после каждого коммита, без вопросов
- **Фильтры per-tab**: каждая вкладка имеет свои фильтры. Изменение фильтров на одной вкладке НЕ влияет на другие
- **Изоляция вкладок**: при работе с одной вкладкой НЕ трогать код других вкладок

### Авторизация (Firebase Authentication, email+пароль)
- Доступ к дашборду закрыт экраном входа `#authGate` (оверлей поверх всего, z-index 99999): поля email/пароль, кнопка «Войти», ссылка «Забыли пароль?» (`sendPasswordResetEmail`). Auth compat SDK подключён в `<head>`
- Логика: `fbApp()` - единая инициализация Firebase (один app для auth и presence); `bootApp()` - идемпотентный запуск дашборда (бывш. `init`, грузит данные); `startPresence(name)` - счётчик; `authGate()` - контроллер входа; `appLogout()` - выход. Дашборд и счётчик стартуют **только после** `onAuthStateChanged` с пользователем
- Топбар: `#authUserBox` (email + кнопка «Выйти») показывается после входа. Persistence LOCAL (вход запоминается)
- **Вход через Google** (`appLoginGoogle`, `signInWithPopup`) - кнопка «Войти через Google» на экране входа, плюс резервный email/пароль. Требует включённого провайдера Google и домена `olegelis.github.io` в Authorized domains
- **Белый список доступа** (`checkAllowed`): доступ разрешён, если email === `ADMIN_EMAIL` ИЛИ есть в `config/allowedEmails` (массив, нижний регистр). Применяется ко **всем** способам входа в `onAuthStateChanged`; не прошёл - авто-`signOut` + сообщение. Правило RTDB: `config/allowedEmails` пишет только админ (`auth.token.email === 'o017ev@gmail.com'`)
- Пользователи email/пароля заводятся в консоли Firebase (Authentication → Users); для Google-входа достаточно добавить email в `config/allowedEmails` (полный доступ) или `config/sheetAccess` (персональная вкладка)
- **Доступ по ролям (вариант A)**: `resolveAccess(user)` → `{allowed, sheet}`. Админ → `RawData`; email в `config/sheetAccess` (`[{email,sheet}]`) → своя вкладка; email в `config/allowedEmails` → `RawData`; иначе отказ. `connectAndLoad` грузит `window._dataSheet` (вкладку пользователя); БФЛ-лист (`loadBflDeals`) - только при полном `RawData`. ⚠ Это разрез «у каждого свой отчёт», НЕ строгая изоляция (таблица/ключ общие - продвинутый юзер может запросить чужую вкладку); строгий вариант - Apps Script-прокси
- **Админ-панель «Доступ»** (`showAccessPanel`, кнопка `#authAccessBtn` в подвале сайдбара, только админу): модал-таблица email + ФИО + выбор вкладки (или «Полный доступ»), `accessAddRow`/`accessSavePanel`; список вкладок - `spreadsheets.get` (фильтр `^RawData`, кроме `RawData`/`RawData_BFL`). Сохраняет в `config/allowedEmails` + `config/sheetAccess` + `config/names` (правила RTDB: запись только админу по `auth.token.email`). **Колонка «Доступ/вкладка» НЕ обязательна**: в селекте есть опция «- без доступа -» (value `''`, дефолт новой строки); контакт без доступа (только email/ФИО, для ЦФО) сохраняется в `config/names` (`accessSavePanel`: `if(nm||!sh)names.push`) и при открытии подхватывается из него (`showAccessPanel` собирает контакты из union `sheetAccess`+`allowedEmails`+`names` с дедупом по email через `addE`/`seenE`) - раньше такой контакт пропадал, т.к. панель читала только allowed+sheetAccess
- **fail-open**: если Firebase/CDN недоступны или нет `apiKey`/`authDomain` - дашборд открывается без входа (барьер от посторонних, а не строгая защита; данные и так тянутся по API-ключу из исходников). `authErrMsg` - человекочитаемые ошибки
- **Рубильник «Сбросить сессии»** (`appLogoutAll`): кнопка `#authLogoutAll` в **подвале сайдбара** (рядом со счётчиком строк, под кнопкой «↻ Обновить данные»), видна только админу (`ADMIN_EMAIL='o017ev@gmail.com'`). Пишет `config/forceLogoutAfter` = ServerValue.TIMESTAMP в Realtime Database; каждая сессия слушает это значение (`watchForceLogout(authMs)`, `authMs` = серверный `auth_time` из `getIdTokenResult`) и при `forceLogoutAfter > authMs` делает `signOut()`. Разлогинивает все сессии (включая админа), вошедшие до метки
- **Общие настройки в RTDB `config/` (требуют правил `.read/.write: auth != null`)**: `config/forceLogoutAfter` (рубильник), `config/kassaLimits` (лимиты реквизитов, `startLimitsSync`), `config/sheets` = `{sheetId, apiKey}` (реквизиты подключения, `startConfigSync` - новое устройство после входа само подхватывает и грузит данные). Всё с localStorage-кэшем и разовой миграцией локальных значений в облако. Кнопка **«↻ Обновить данные»** (`refreshData`, подвал сайдбара) - повторный `connectAndLoad`

### Живой счётчик «Онлайн» (Firebase Realtime Database)
> Подпись переименована «Сейчас на сайте» → «Онлайн» (топбар + попап). Каждый пульс пишет также **историю посещений** `activity/{emailKey}/days/{YYYY-MM-DD}/{sessionUuid}` = `{first,last,dev}` + meta `lastSeen/name/email` (`logActivity` в `startPresence`; emailKey = email с заменой `.#$[]/`→`_`). Клик по сотруднику в попапе (только админу) → `showEmployeeActivity(email,name)`: читает `activity/{emailKey}`, агрегирует по дням (сессии, ≈время онлайн = Σ span сессий, мин 20с), показывает KPI (последний визит/активных дней/сессий/время) + полоски по дням + устройства. **Требует правило RTDB** `activity` (`.read` админу, `.write` `auth != null`). История копится только с момента включения. Презенс-запись теперь содержит и `email`.
- Топбар: `#presenceBox` / `#presenceCount` (скрыт, пока не настроен Firebase). Firebase compat SDK подключён в `<head>` (CDN). Конфиг - константа `FIREBASE_CONFIG` (apiKey/authDomain/databaseURL/projectId/...); при пустом `databaseURL` `startPresence()` тихо выходит, дашборд работает как обычно
- После входа пишет `presence/{uuid}` = `{ts: ServerValue.TIMESTAMP, name: <email>, dev: <устройство>}` (`dev` = `uaShort(navigator.userAgent)`, напр. «📱 Android · Chrome»); пульс каждые 20с; авто-удаление `onDisconnect().remove()` + `pagehide`/`beforeunload`. Счёт = сессии с `ts` за последние 60с с поправкой на `.info/serverTimeOffset`. Всё в try/catch - не влияет на дашборд
- Клик по `#presenceBox` → попап `showPresenceList()`: список онлайн, сгруппированный по email (×N вкл.), под каждым - устройства (`dev`) и время последней активности; безымянные старые вкладки (кэш до ввода имён) - «устройство неизвестно». Список в `window._presenceList`, живо обновляется при открытом попапе

### Источник данных
- Google Sheets API (read-only, API Key)
- Лист `RawData`, первая строка - заголовки
- Запрос: `valueRenderOption=UNFORMATTED_VALUE&dateTimeRenderOption=SERIAL_NUMBER`
- Даты приходят как Excel-серийные числа → `parseDate` конвертирует
- Архитектура: один сводный лист, данные собираются через IMPORTRANGE из источников

### Пресеты отчётов (`config/presets`)
- Пресет = именованный частичный снимок фильтров вкладки (`{id, name, f:{...поля _tabFilters[tab]...}}`). Поддержаны 5 отчётов: **БАНК, ОПиУ, ДДС, ОСВ, ФОТ** (`PRESET_TABS`); схема полей на отчёт - `PRESET_FIELDS` (типы: select / toggle / years / months / dirs; динамические списки годов/направлений из `RAW`). Пустые мультиполя = «все»
- **Динамический (относительный) период** - всегда считается от текущей даты при применении: БАНК через поле `preset` (`setPreset` считает от now - Сегодня/Этот месяц/Этот год/…); ОПиУ/ДДС/ОСВ/ФОТ через поле `rel` (`cur_month`/`cur_quarter`/`cur_year`/`ytd_month`/`all`, для ОСВ ещё `cur_day`) - резолвится `_presetApplyRel(tab,rel)` в `presetApply` и перекрывает ручные `years`/`months`. Пустой `rel` = фиксированный период по выбранным годам/месяцам
- Хранение: **Firebase RTDB `config/presets`** (общие для всех устройств) + localStorage-кэш (`reportPresets`). `_presetsSave` (localStorage + RTDB set), `startPresetsSync` (подписка, вызывается вместе с `startPlansSync` после входа), `_presetsNormalize` (RTDB-массив/объект → массив). Требует правил БД на запись `config/presets`
- Редактор - **Настройки → «Пресеты отчётов»** (`showPresetsPanel`, только админу): модал с переключателем отчёта (`_presetSelReport`), списком пресетов и формой (`_presetFormHtml`, `_presetSave`, `_presetEdit`, `_presetDelete`)
- Применение - выбор пресета встраивается **инлайн в строку фильтров** отчёта (НЕ отдельной строкой): `_injectPresetBar` вставляет `.preset-inline` (выпадашка + кнопка «Настроить» админу) первым элементом в `.tab-filters` (Банк) или `.dds-extra-filters` (ОПиУ/ДДС/ОСВ/ФОТ). Идемпотентно; `MutationObserver` на `#mainContent` (`_setupPresetObserver`) переинжектит после любой перерисовки (в т.ч. прямых `renderBank` и т.п.). `presetApply(tab,id)` мёржит `f` в `_tabFilters[tab]` и ре-рендерит (для банка вызывает `setPreset`). ⚠ Имя `applyPreset` занято дат-чипами фильтр-бара - пользовательские пресеты называются `presetApply`. Свой эскейпер `_pesc` (глобального `esc` нет - он локален в каждой render-функции)
- **Строка-сводка фильтров**: у Банка - своя (в `renderBank`, `fSumm`); для **ДДС/ОПиУ/ОСВ/ФОТ** общая строка `.tab-filter-summary` вставляется под баром фильтров через `_injectPresetBar` (контент - `_filterSummaryInner(tab)`: Пресет/Год/Месяц/Направление, +Счёт для ОСВ, +Статья/Подстатья/Сотрудник для ФОТ, +тумблеры; обновляется по data-sig, чтобы не зациклить observer). Кнопка «× сбросить всё» → `_resetTabFilters(tab)` (чистит years/months/dirs/accounts/articles/subarticles/counterparties/rel + тумблеры + активный пресет)
- **Активный пресет / снятие**: `_activePreset[tab]` помнит выбранный пресет → выпадашка показывает его (опция `selected`); выбор «- не выбран -» (`presetApply(tab,'')`) снимает пресет и возвращает период к «всё время» (банк - `setPreset('all')`, прочие - `rel=''`, `years=[]`, `months=[]`). Ручной клик по дат-чипу (`applyPreset`) и `bankResetAllFilters` тоже сбрасывают `_activePreset` (и банк-резет теперь чистит период целиком). В сводке Банка «Фильтры:» добавлена строка **«Период: …»** (метка пресета/диапазон дат + имя активного пресета)

### Паттерн рендера
Каждая вкладка - функция `renderXxx(f)`, где `f = getFilters()`. Функция полностью перестраивает innerHTML вкладки. Вызывается из `renderActiveTab()`.

## Вкладки

### 1. Банк и касса (`bank`)

#### Артефакты
1. **Фильтр-бар** - даты + пресеты + extra-bar с мультивыборами
2. **KPI-бар** - 4 карточки: Поступления / Списания / Сальдо / Счетов + Cash Runway
3. **Свод по счетам** - Денежные средства (ООО, ИП) + До налогового оформления (Карты ФЛ, Кассы ЦФО)
4. **Графики** - верхний (по годам/месяцам) + нижний (по дням, клик → фильтр)
5. **Таблица операций** - 22 строки, пагинация 500, клик на строку → модал карточки

#### Extra-фильтры (строка под основным фильтром)
Мультивыбор с чекбоксами: **Направление / ID Offer / Статья / Подстатья / Фин. операция / Контрагент**
- У всех дропдаунов (кроме Направления) есть **поле поиска** по значениям
- Применяются ко **всем блокам листа** (свод, KPI, графики, таблица). Применение - при закрытии дропдауна (полный `renderBank`)
- Списки значений в дропдаунах строятся из `dataBase` (до extra-фильтров), чтобы выбор не «схлопывал» список
- Кнопка `× сброс` сбрасывает все фильтры таблицы
- Поля состояния: `offerIds, articles, subarticles, finOps, secondSides` в `_tabFilters.bank`

#### Тумблер «Будущие оплаты» (`_tabFilters.bank.includeFuture`)
- вкл (по умолчанию) → добавляются плановые/будущие платежи с датой позже сегодня
- выкл → только операции по текущий день включительно (по `DATE_DDS`/`DATE_OPIU`)
- Применяется ко **всему листу Банк**: свод, KPI, графики, таблица операций

#### Лимиты реквизитов (KPI-карточка «Лимиты счетов»)
- Карточка в KPI-баре показывает статус: «Превышение: N» (красный) / «В норме» (зелёный) / «Не настроено» / «Нет счетов»
- Лимиты задаются для **всех именованных реквизитов**: счета ООО/ИП, Карты ФЛ, Кассы (исключая «без реквизитов»). Остаток = `total` счёта (с учётом фильтров)
- Клик → попап (широкий): таблица Тип / Реквизит / Остаток / Лимит (редактируемое поле) / Статус. Изменения применяются сразу
- Лимиты хранятся в **Firebase RTDB** (`config/kassaLimits` = `{accName: number}`) - **общие для всех устройств**; localStorage (`kassaLimits`) остаётся локальным кэшем. Функции `_kassaLimits` (объект), `_kassaSaveLimits` (пишет в localStorage + RTDB), `startLimitsSync` (подписка на `config/kassaLimits`, при изменении - `_kassaLimits` обновляется и `renderBank`, если активна вкладка; разовая миграция локальных лимитов в облако через `_limitsMigrated`), `kassaSetLimit`, `showKassaLimitsPopup`. `startLimitsSync()` вызывается вместе с `startPresence()` после входа
- При закрытии попапа - `renderBank` обновляет карточку

#### Cash Runway
- Текущий баланс (saldo из отфильтрованных данных) ÷ средний операционный расход × 30
- Расходы: только FIN_OP начинается с `001_`, последние 90 дней до текущего месяца
- Клик на карточку → попап с детализацией по месяцам

### 3. ОПиУ (`opiu`)
- Отчёт о прибылях и убытках (ОПиУ)
- Использует `DATE_OPIU`
- Extra-фильтры: **Год** (мультивыбор) / **Месяц** (мультивыбор) / **Направление** (мультивыбор) / **Период**
- Категории расходов берутся из колонки **АНАЛИТИКА** (`COL.ANALYTICS`). Массив `CATS`:
  `Прямые / Переменные`, `Прямые / Постоянные`, `Косвенные / Переменные`, `Косвенные / Постоянные`, `Налоги / проценты / амортизация`, `EBITDA-корректировки`, `Вывод чистой прибыли`
- Секции отчёта: ВЫРУЧКА → ПРОИЗВОДСТВЕННЫЕ РАСХОДЫ (Прямые) → КОСВЕННЫЕ РАСХОДЫ → EBITDA → РАСХОДЫ НИЖЕ EBITDA (налоги + EBITDA-корректировки) → ЧИСТАЯ ПРИБЫЛЬ → РАСПРЕДЕЛЕНИЕ (вывод прибыли)
- **EBITDA-корректировки** - непрофильные/разовые расходы (корпоратив, обучение собственника и т.п.). Значение аналитики в Google Sheets должно быть ровно `EBITDA-корректировки`
- **Тумблер «Включить EBITDA-корректировки в EBITDA»** (`_tabFilters.opiu.ebitdaInclBelow`):
  - выкл (по умолчанию) → корректировки идут ниже EBITDA, на сам EBITDA не влияют
  - вкл → корректировки в составе косвенных расходов, уменьшают EBITDA
  - чистая прибыль одинакова в обоих режимах (меняется только позиция относительно линии EBITDA)
- **Переключатель «Расходы: по аналитике / по статьям»** (`_tabFilters.opiu.expFlat`, селект в фильтр-баре): меняет ТОЛЬКО представление детальной части расходов, не расчёты. По аналитике (дефолт) - текущие секции по категориям (Прямые/Косвенные/EBITDA/…). По статьям - плоский список **Статья → Подстатья** (как выручка), но С ДЕЛЕНИЕМ на «РАСХОДЫ ДО EBITDA» → строка EBITDA → «РАСХОДЫ НИЖЕ EBITDA» → ЧП (тумблер «Корректировка EBITDA» так же двигает «EBITDA-корректировки» между блоками). Наборы строятся `mergeArts(cats)` - объединяет `exp[cat].arts` нужных категорий аналитики по `ARTICLE_CODE`→`ARTICLE_NAME`: `expAbove` (Прямые/Косвенные [+ корректировки если inclBelow]), `expBelow` (Налоги [+ корректировки если !inclBelow]); `expArtRows(artObj,idPrefix,secLabel)`. Сводный блок (ВЫРУЧКА/РАСХОДЫ/EBITDA/ЧП), `totalExpMap`/`netMap`, EBITDA/ЧП и все итоги в обоих режимах идентичны (expAbove∪expBelow = те же 6 категорий = `totalExpMap`); маржа/валовая показываются только в режиме по аналитике. «Вывод прибыли» (127) - отдельной секцией РАСПРЕДЕЛЕНИЕ в обоих режимах
- **Расчётный транзит почты БФЛ↔АУ** (`_tabFilters.opiu.postSplit`, чекбокс «Разделение БФЛ / АУ (почта)»): виртуальные строки (в RAW/Sheets НЕ пишутся), показываются ТОЛЬКО когда выбран **ровно один** контур ∈ {`БФЛ - Банкротство физических лиц`, `АУ - Арбитражный управляющий`} (иначе чекбокса нет: агрегат/пусто/2+/любое др. направление; САУ ≠ АУ). Триггер-кейс: БФЛ + подстатья `112_Депозиты и госпошлины` + |списание| ∈ {25000, 50000} + непустой `ID_Offer`; дедуп по `ID_Offer` (1 кейс = 1 транзит **20 000 ₽** фикс, период = `DATE_OPIU` депозита). Инъекция ПОСЛЕ цикла агрегации и ДО расчёта карт (вошло в `totalExpMap`/`ebitdaMap`/`netMap`): в БФЛ - расход −20000 в `exp['Прямые / Переменные']`, статья (ARTICLE_CODE) `112_Расходы на производство` (мёрджится с существующей группой), подстатья `112_Расходы на публикации (справочно)`; в АУ - доход +20000 в `rev` подстатья `120_Поступление на публикации (справочно)` (АУ-вид сканирует RAW БФЛ теми же фильтрами периода). Баланс: Σ БФЛ = Σ АУ = N×20000. ЧП: БФЛ −20000/кейс, АУ +20000/кейс; агрегат и др. направления не затронуты. Работает в обоих представлениях (по аналитике/по статьям). Допущение: почта фикс 20000/ID; при факте заменить
- В **ДДС** аналитика не используется: классификация по `FIN_OP` (`001_/002_/003_/other`). EBITDA-корректировки попадают в раздел по своему `FIN_OP`, а не по аналитике

### 5. Юнит-экономика (`marketing`)
> Вкладка переименована «Маркетинг» → «Юнит-экономика» (в меню и заголовке, `TAB_TITLES.marketing`); внутренний ключ `marketing` и вся логика/функции (`renderMarketing`, `mkt*`) сохранены. Доменные термины «доля маркетинга», «маркетинговый расход» в коде не менялись.
- Метрики: **CPMT** (Cost Per Meeting, стоимость встречи), **CPO** (стоимость сделки), **CPF** (стоимость исполнения) + **Конверсия встреча→сделка** - верхнеуровневые. CPL скрыт по решению пользователя (логика/списки в коде сохранены - не показывается в KPI и таблице)
- **Варианты «по ФОТ»** (`meetFot`/`cpoFot`): те же знаменатели (встречи/сделки), но в расходах - только ФОТ-подстатьи, причём **базы разные**:
  - **CPMT по ФОТ** (`meetFot`) = любое КО (колл-центр: КО, КО2, …) + ОМ (маркетинг) - `mktFotMeetMatch`
  - **CPO по ФОТ** (`cpoFot`) = **весь набор CPO без рекламы 300_*** (ЗП 111_ всех отделов АО/КО/КО2/ОМ/ОП + контроль качества 226_) - `mktFotCpoMatch = mktMatch('cpo',sub)&&!sub.startsWith('300_')`
  - Отдельные бакеты `costs.meetFot` / `costs.cpoFot` и ключи `_mktTxn['meetFot|pk']`/`['cpoFot|pk']`. АО, реклама 300_* и 226_ - НЕ входят
  - На графиках: **4 холста в ряд** - (1) **Доля маркетинга в выручке** в % (`mktChartShare`, `buildShareChart`, своя шкала, может быть >100%), (2) CPMT + CPMT по ФОТ (`mktChartMeet`), (3) CPO + CPO по ФОТ + **линия конверсии встреча→сделка на правой оси `y1` в %** (`mktChartCpo`; серия `{valueFn:convAt,pct:true}`, пунктир), (4) CPF (`mktChartCpf`) Показываются и в KPI, и в таблице рядом с полными CPMT/CPO; полные (по всей воронке) метрики сохранены. Расшифровка `mktShowCostModal('meetFot')` мапит на `cpoFot`
- **CPMT - стоимость встречи** (внутренний ключ метрики `meet`): использует **те же расходы воронки, что и CPO** (`costs.meet=costs.cpo`), делённые на число встреч. Встреча = «Дата создания сделки» (`RawData_BFL`, массив `meetings`, ⚡ авто для БФЛ). Связь метрик: **CPO = CPMT ÷ конверсия(встреча→сделка)**. Расшифровка расходов CPMT = расшифровка CPO (`mktShowCostModal('meet',…)` мапит на `cpo`). На графике CPMT и CPO - **две линии на одном холсте** (`mktChartCpo`, с легендой); CPF - отдельный холст
- KPI-карточки: под значением - строка динамики, сравнивающая **два последних ЗАПОЛНЕННЫХ периода** (где метрика считается), напр. «↑ 300% Февраль 2026 к Январь 2026»; пустые будущие месяцы со случайным расходом игнорируются (фильтр `periods.filter(metricAt!=null)`)
- **Конверсия встреча→сделка** = кол-во сделок ÷ кол-во встреч (выше = лучше, рост зелёный). Отдельная KPI-карточка + строка «Конверсия воронки» в таблице (ячейки `mkt-conv-{pk}`)
- **Компактная таблица**: каждый блок метрики = 3 строки - именованная строка с **результатом в той же строке** (CPMT/CPO/CPMT·ФОТ/CPO·ФОТ/CPF, ячейки `mkt-val-{metric}-{pk}`), ниже «Расходы» и «Количество …» (мельче, серым). Отдельной строки-заголовка нет. Конверсия и «Доля маркетинга в выручке» - результат тоже в именованной строке
- **Доля маркетинга в выручке** = (расходы маркетинга) ÷ выручка по ОПиУ. Расходы маркетинга (`costs.mktShare`, `mktSpendMatch`) = **все `300_*` + `111_Заработная плата ОМ`** (отдел маркетинга). Выручка (`revByP`) считается как в ОПиУ: поступления выбранного направления (`type='поступление'` или статья `120_`, `inc>0`) по дате ОПиУ. KPI-карточка (рост = красный) + блок в таблице (Выручка / Расходы маркетинга / Доля в выручке). **Кликабельны и Выручка, и Расходы маркетинга** → `mktShowCostModal(metric,pk)`: `'mktShare'` - расходы маркетинга, `'rev'` - выручка (поступления, строки в `_mktTxn['rev|'+pk]`). Модал обобщён флагом `isRev` (COL.INCOME/var(--income) для выручки, COL.OUTCOME/var(--outcome) для расходов; заголовок/ИТОГО/чипы подстатей по знаку)
- Расходы берутся из RAW по подстатьям (ARTICLE_NAME), матчинг `mktMatch` = точный список `MKT_SUBART` + префиксы `MKT_PREFIX`:
  - CPL: `111_Заработная плата АО`, `111_Заработная плата ОМ` + **все `300_*`** (Лидогенарация, Акция Приведи друга, Выплата Агентам, Дизайн и полиграфия, Медиаразмещение, Маркетинг прочее)
  - CPO: `111_Заработная плата АО/КО/КО2/ОМ/ОП`, `226_Контроль качества` + **все `300_*`**
  - CPF: `111_Заработная плата АУ/ОИ/ОС` + фиксированный список `112_*` (адвокатский запрет, возвраты, депозиты, СРО, почтовые, прочие платежи, публикации, торги, экспертиза)
  - ⚠ Подстатей «300_Реклама / маркетинг» и «244_Контроль качества» в данных НЕ существует - не возвращать
- **Направления не смешиваются**: фильтр «Направление» - одиночный выбор (`activityDir`), опции «Все направления» НЕТ; по умолчанию `БФЛ - Банкротство физических лиц`; расходы фильтруются строго по выбранному
- `112_Распределение КМ` и `112_Траспортные расходы` в CPF **не включаются** (решение пользователя)
- Фильтры в стиле ОПиУ: **Год** (мультивыбор) / **Месяц** (мультивыбор) / **Направление** (одиночный) / **Период** (разрез). Пресетов и выбора дат нет. По умолчанию - текущий год, разрез помесячно
- График динамики CPO/CPF: при выбросе (>3× медианы) шкала Y ограничивается ~медиана×2.5 - иначе всё «сплющивается» в полосу. **У каждой точки подписано значение** (плагин `valueLabels`, формат К/М); на графике CPMT+CPO 1-я линия подписана сверху, 2-я снизу (чтобы не накладывались). Пиковые значения, выходящие за шкалу, подписываются числом над графиком (`▲ N`)
- Знаменатели (кол-во лидов/сделок/дел) - **ручной ввод** по периодам, **отдельно для каждого направления**
- **Для направления БФЛ** все количества считаются **автоматически** из листа Google Sheets `RawData_BFL` (`loadBflDeals` → `RAW_BFL={leads,meetings,paid,done,deals}`):
  - лид = «Дата создания Лида»; **встреча = «Дата создания сделки»** (массив `meetings`); сделка = «Дата входа в стадию "Полная/частичная оплата"»
  - исполнено (CPF) = «Дата завершения сделки» для стадий `Производство. Акты подписаны, работы завершены`, `Отдел сопровождения. Акты подписаны` (массив `DONE_STAGES`) **ИЛИ любой стадии, содержащей «работы завершены»** (`isDoneStage`)
  - «Дата создания сделки» = **встреча** (используется в метрике СВ и конверсии встреча→сделка)
  - **Тех. специалисты исключаются из статистики количеств** (лиды/встречи/сделки/завершения) по полю **«Кем создана сделка (текст)»** (`iCreatedBy`, не «Ответственный»): `EXCL_RESP_EXACT` (точное совпадение: Павличенко Елизавета Сергеевна, Шелков Александр Сергеевич) + `EXCL_RESP_PREFIX` (по префиксу: Гагарина Варвара). В `deals[]` (дебиторка) такие строки **остаются** - исключение только из количеств метрик
  - Авто-поля: ручной ввод для них скрыт (значок «⚡ авто» убран по просьбе пользователя). Лист не критичен: при его отсутствии - ручной ввод
  - **Количества кликабельны** (для авто-полей БФЛ): клик по ячейке кол-ва встреч/сделок/завершений/лидов → модал `mktShowCountModal(field,pk,label)` со списком записей (дата/ФИО/ID_Offer/№ договора/стадия/ссылка Bitrix24). Записи хранятся в `RAW_BFL.{leadsRows,meetingsRows,paidRows,doneRows}` (объекты `{date,fio,offer,contract,stage,responsible,url}`), раскладываются по периодам в `window._mktCntRows[field+'|'+pk]`. Для ручного ввода (не БФЛ) расшифровки нет
- Подписи графиков - **чипы с цветными маркерами** (`mktChip`, `.mkt-legend`, фикс. высота 34px, wrap) вместо текста через «·» (чтобы не сливались). Справка формул (`formulaHtml`) - структурная: группы Воронка / По ФОТ / Исполнение / Доля, каждая метрика = цветная плашка + формула (`fItem`/`fGroup`)
- В отчёт попадают **только периоды с маркетинговым расходом** (`mktMatch`), а не любые списания - будущие/посторонние месяцы не раздувают график. Подписи оси X сокращены («Янв '26»), полное имя периода - в тултипе; **`autoSkip:false` + фикс. угол 60°** - чтобы ось X была одинаковой на всех 4 графиках (иначе из-за разной ширины области построения подписи прореживались по-разному)
- Хранение ручного ввода: **localStorage** (`mktCounts` = `{dirKey:{periodKey:{leads,orders,fulfilled}}}`, dirKey=`__all__` для «Все направления»; старый плоский формат мигрируется автоматически)

### 6. Структура расходов (`expenses`)
- Все расходы как в ОПиУ, но **без рентабельностей/EBITDA/прибыли** - только состав и веса
- По дате ОПиУ; группировка: **аналитика (категория) → подстатья**
- Колонки: **Сумма / Доля в расходах / % от выручки**; строка ИТОГО

Опции статья/подстатья - из направление-фильтрованных данных; выручка (база %) - до фильтров статья/подстатья. Все дропдауны авто-применяются по клику снаружи
- Визуализация: **donut** долей категорий + горизонтальный **рейтинг топ-подстатей** (% от выручки в тултипе) + **«Сравнение расходов по периодам»** - накопительный стэк-бар, разбивка **по подстатьям** (`perSub` по `ARTICLE_NAME`, топ-8 по сумме + «Прочее»; периоды по `periodType`)
- KPI: Выручка / Расходы всего / Доля расходов в выручке / Категорий

### 7. ОСВ по счетам (`osv`)
- Оборотно-сальдовая ведомость по реквизитам (`renderOSV`), строго по `DATE_DDS`

- Фильтры в стиле ДДС/ОПиУ: **Год** (мультивыбор) / **Месяц** (мультивыбор, зависит от годов) / **Счёт** (мультивыбор с поиском) / **Направление** / **Разрез**. Дат-инпутов нет
- Разрезы (`periodType`): `all` (4 колонки) / `year` / `month` / `day` - на каждый период четвёрка **Сальдо нач. / Дт / Кт / Сальдо кон.** (нач. периода = кон. предыдущего); день ограничен 62 днями
- Невыбранные месяцы внутри диапазона вливаются в переходящее сальдо (баланс сходится); в `all` - в «Сальдо нач.»
- Клик по строке счёта ничего не делает (выбор счёта - только через фильтр)

- Закреплены при прокрутке: обе строки шапки (sticky top 0/30px) и левая колонка «Счёт / Реквизит» (sticky left)
- Отрицательное сальдо подсвечивается красным (индикатор ошибки в данных)
- Тумблер «Строки» (`rowDim`): `direction` (по направлениям, **дефолт**) / `account` (по счетам) - измерение строк таблицы; вынесен в **правый угол** фильтр-бара (`margin-left:auto`)
- Тумблер «Без вход. сальдо» (`noOpening`): выкл (дефолт) - сальдо с входящим остатком; вкл - сальдо считается с нуля, показывает только обороты выбранных периодов (без начального остатка и переходящего)

### 8. Дебиторка БФЛ (`debtbfl`)
- Задолженность по договорам БФЛ (`renderDebtBfl`): **сумма договора** из листа `RawData_BFL` (колонка «Сумма»), **оплачено (нетто)** = Поступления − **только `112_Возвраты клиентам`** (прочие списания по ID - госпошлины/публикации и др. расходы дела - оплату НЕ уменьшают) из `RawData` **только с направлением `БФЛ - Банкротство физических лиц`**, связь по **ID_Offer**. В модале расшифровки показываются поступления + возвраты клиентам

- **«⚠ Нет в Bitrix24»** - тумблер-режим: оплаты по ID, отсутствующим в листе сделок (контроль расхождений). **Сверка по уникальному ID Bitrix24** (`_arLeadId` - первые цифры до «|», индекс `byLeadId`): если по полному ID_Offer сделки нет, но lead-id совпадает с существующей сделкой - в строке и модале показывается найденная запись Bitrix24 (ФИО/№ договора/сумма/стадия/менеджер/дата/ссылка) с пометкой «✓ найдено в Bitrix24 по ID»; если не найдено и по lead-id - «✗ нет даже по ID». Поля orphan-объекта: `isOrphan, bxMatch, leadId, bxSum`

- В режиме «Нет в Bitrix24» ID тоже виден и кликабелен - модал показывает предупреждение об отсутствии сделки и список оплат
- KPI: Сумма договоров / Оплачено нетто (%) / Дебиторка (%) / Договоров с долгом (+счётчик без сделки)
- Фильтры: поиск (debounce 300мс) / Стадия (мультивыбор+поиск) / Менеджер («Ответственный (текст)», мультивыбор+поиск, `_arDD`) / Давность оплаты (select) / «Только с долгом» (вкл по умолчанию)
- **Закрытые стадии ВКЛЮЧЕНЫ по умолчанию** - по ним мог остаться долг («перестал платить», недоплата при завершённых работах). Тумблер «Скрыть закрытые (N)» (`hideClosed`) убирает их (маркеры `AR_CLOSED_MARKERS`: работы завершены / перестал платить / расторг / брак / потерян / не отвечает / дорого и т.д.)

- Колонка **«Дата сделки»** после ID_Offer; клик по заголовку - сортировка по дате ▲/▼/сброс (`dateSort`, `arToggleDateSort`); по умолчанию сортировка по долгу
- Состояние: `search, onlyDebt, stages, resps, payCat, orphansOnly, hideClosed, overOnly, cutoffOn, dateSort` в `_tabFilters.debtbfl`
- Если `RAW_BFL` не загружен - заглушка с подсказкой переподключиться

### 9. Займы сотрудникам (`loans`)
- Учёт займов сотрудникам (`renderLoans`): **выдача = списание** (деньги уходят сотруднику), **возврат = поступление**. Группировка по контрагенту (`COL.SECOND_SIDE` - кому заняли)
- **Все операции на кассе займов - перемещения в колонке ПОСТУПЛЕНИЕ со знаком**: выдача = `+X`, возврат = `-X` (списаний обычно нет). **Знаковая модель**: `amount = inc + out` на строку; `amount>0` → выдача (`issued`), `amount<0` → возврат (`repaid`); **остаток (долг) = Σ amount = issued − repaid** = сальдо кассы. ⚠ Нельзя брать возврат как `abs(любого поступления)` - тогда выдача (+) и возврат (−) оба считались бы возвратом и долг задваивался (баг «долг 660» вместо 0)
- Операции определяются по **«Реквизиты счёта» (касса)** (`COL.ACCOUNT`), содержащему **«займ» и «сотрудник»** (`isLoanRow`). **Статья/подстатья НЕ участвуют** (по решению пользователя)
- **Сверка сумм**: раскрывающийся блок «🔎 Сверка» (`<details>`) показывает разбор по `реквизитам счёта (касса)` (строк / выдано / возвращено). Если есть строки с «займ» в реквизитах без «сотрудник» (иная займовая касса) - выводится ⚠ с их числом (`looseExtra`)
- Остаток = Выдано - Возвращено (положительный = сотрудник должен; отрицательный = переплата, зелёным `+X`); `%` погашения = Возвращено / Выдано (прогресс-бар в таблице)
- KPI: Выдано / Возвращено (% от выданного) / Остаток непогашено / **Статусы** (чипы Погашено/Частично/Не возвращал). KPI считаются по текущей выборке
- Визуализация: **портфельная сводка** (стопочная полоса Возвращено/Остаток в % + статус-чипы) вместо старого «Топ по остатку». Таблица: Сотрудник (с цветной точкой статуса) / Выдано / Возвращено / **Остаток (акцент)** / Погашение (прогресс-бар) / **Без возврата** (дней с посл. возврата, цвет по давности ≤30/≤90/>90) / Послед. возврат / Опер. Группировка: **должники сверху, погашенные** - отдельной секцией с разделителем «Погашенные · N» и приглушением. Зебра/hover, мягкая палитра (зелёный `#2e9e6b` / янтарный `#e0894a` / красный `#d35450`). Дубль-заголовок над таблицей убран
- **График динамики** (`loanChartDyn`): по месяцам столбцы Выдано (`#e0894a`) и Возвращено (`#2e9e6b`) на **левой оси `y`** + линия накопленного остатка (`#3a6ea5`) на **правой оси `y1`** (разные шкалы - остаток обычно крупнее месячных потоков). Наглядно, что выдачи и возвраты идут не синхронно. Данные в `window._loanDyn`; считается по `shown` (учитывает фильтры)
- Клик по строке → модал `loanShowDetail`: сводка выдано/возвращено/остаток + движения по сотруднику **в формате окна ДДС** (15 колонок, клик по строке → `ddsShowRecordCard`); строки в `window._loanRows`, движения в `window._loanMoves`
- Фильтры (одна строка): даты / поиск сотрудника (debounce 300мс) / тумблер «Только непогашенные». Состояние: `dateFrom, dateTo, search, onlyDebt` в `_tabFilters.loans`

## Группа «Контроль»

### 7. Дубли (`dupes`)
- Поиск **полных дублей** записей: совпадение **всех ячеек строки** (вся строка целиком, не только 15 известных колонок) после trim (`renderDupes`). Режим один - все ячейки, без исключений
- KPI: групп дублей / лишних строк / задвоено поступлений / задвоено списаний (лишние = все строки группы сверх первой)
- Таблица групп (макс 200) - точная копия таблицы «Операции» Банка (тот же `colgroup` c классами `c-*`, 15 колонок, `txn-table`); клик на строку → карточка операции (`dupesShowCard`, строки в `window._dupesRows`). Лишние строки выделены красным
- Поясняющая подпись (`checkNote`): «Проверено N из M строк · отброшено K пустых (Поступление и Списание = 0); из них перемещений: P (в ДДС не показываются)» - объясняет расхождение между «всего строк» (RAW.length), проверкой дублей (applyBaseFilters - без нулевых сумм) и ДДС (без перемещений)
- Кнопка **«Сформировать отчёт»** (`dupesPrintReport`) - открывает печатную версию (окно с автопечатью → печать или сохранение в PDF для бухгалтера). Данные в `window._dupesGroups`/`_dupesMeta`
- Удаление дублей - только вручную в Google Sheets (дашборд read-only)

### 8. Недозаполненные данные (`incomplete`)
- Проверка обязательности полей по регламенту заполнения (`renderIncomplete`)
- **Ошибки** (красные): пустые ДДС / ОПиУ / Тип / Статья / Подстатья / Направление / Фин. операция; нечисловые Поступление/Списание (0 - валидное значение); несовпадение первых 3 цифр кода Подстатьи и Статьи; **перемещение без пары** (перемещения группируются по дате ДДС + |сумме Поступления|: должна быть пара −X/+X с суммой 0; нулевое перемещение - тоже ошибка)
- **Предупреждения** (жёлтые, допустимая временная пустота): ФНС, Реквизиты счёта (заполняет фин.менеджер), Аналитика при типе «списание». ID Offer не проверяется
- KPI: строк с ошибками / только предупреждения / корректных / проверено. Чипы-разбивка нарушений по полям
- Таблица (лимит 500): колонка «Проблемы» + 15 колонок как в Банке, проблемные ячейки подсвечены; клик → карточка (`incShowCard` переиспользует `dupesShowCard`)
- Строки совсем без дат включаются в проверку независимо от дата-фильтра
- Фильтр по датам; группа в меню «Контроль» - сюда добавлять будущие проверки качества данных

### 9. Аномалии (`anomaly`)
- **Жёсткие (детерминированные) правила** (`renderAnomaly`), без статистики - по решению пользователя (статистика давала много шума). Read-only
- Движок: массив `RULES`, каждое правило = `{id,label,where(r),checks:[…]}`. Каждый check = `{field,fieldName,expect}` (нарушение, если `norm(actual)` НЕ содержит `norm(expect)`) ИЛИ `{field,fieldName,requireFilled:true}` (нарушение, если поле пустое). `norm` = lowercase + удаление всего кроме букв/цифр (чтобы «999_Техническая операция» матчила «Техническая операция», «002_Финансовая операция» - «Финансовая»). `code3(r)` = первые 3 цифры `ARTICLE_CODE`/`ARTICLE_NAME`. Добавить правило = дописать объект в `RULES` (одно правило может иметь несколько checks → несколько строк-нарушений)
- Текущие правила: **Перемещение → Фин. операция «Техническая операция»**; **Статья 300* → Аналитика «Прямые / Переменные»**; **Статья 112* → Аналитика «Прямые / Переменные»** (300/112 не применяются к перемещениям); **Списание → только со знаком «−»** (`outsign`, `is127`-стиль `where`: непереместительная строка с Списанием > 0 → ошибка, валидатор `ok:a=>parseNum(a)<=0`; перемещения исключены - их знак проверяет `movebal`); **Статья 127** (`div`, `is127` = код статьи 127 ИЛИ подстатья содержит «дивиденд») → Аналитика «Вывод чистой прибыли» + Фин. операция «002_Финансовая деятельность» (валидатор `okFin002`: norm содержит `002`+`финанс`) + обязательный контрагент (ID_SecondSide); **112_Платежи в СРО** (`sro`, подстатья содержит «сро») → направление только АУ/САУ (по префиксу направления, кастомный `ok`)
- **Счёт ООО/ИП → ФНС «да»** (`fns`): если «Реквизиты счёта» начинается с ООО/ОАО/ЗАО/ПАО/АО или ИП (классификация как в БАНКе), ФНС должно быть «да» (принимаются `да/true/1/+` через `fnsYes`); перемещения исключены. Поддержан check с кастомным валидатором `ok:(actual,row)=>bool`
- **ID_Offer → сверка со справочником Bitrix24** (`offerref`, отдельный блок): справочник = **`RAW_OFFERS.deals` (лист `RawData_ID_Offer` - сделки ВСЕХ направлений**, загрузчик `loadOfferRef`); откат на `RAW_BFL.deals` (только БФЛ), если общий лист недоступен. ⚠ Важно: `RawData_BFL` = только БФЛ, поэтому БФЛ-операции, ссылающиеся на сделки других воронок (Аварком/Автоправо, суффиксы -АК/-АП), раньше ложно флагались «нет в справочнике» - теперь сверяются с полным листом. Для строк направления БФЛ с непустым ID_Offer. **Главный матч - по системному ID (lead-id, число до «|»)**: если `refLead[lead]` есть - та же сделка, НЕ аномалия (ФИО/№ договора могли изменить, ID - нет). Запасные матчи: полный ID (`refOffer`/`_arNormId`), № договора (`refContract`), ФИО (`refName`). В колонке **«Ожидается»** - что видно в справочнике по этому **lead-id** (цифры до «|»): `refLeadDesc(lead)` = представительный offer + годы и кол-во записей (`«offer · 2024 (7), 2025 (6)»`, под одним ID бывает несколько сделок; индекс `refLead[lead]={offers,years}`, год из `created`/`dateContract`). Если lead-id есть ID, но его нет в справочнике → «нет в справочнике (ID N)»; если ID вообще нет (в поле только ФИО) → «ID не указан». **Повторяющиеся ID агрегируются** (`offAgg`, `aitems`/`agg`/`count`/`rows`); клик → модал-список операций (формат ДДС, `anomShowCard` → `window._anomMoves`)
- **`ebitda`**: Аналитика «EBITDA-корректировки» (`norm` содержит `ebitda`) → Фин. операция «002_Финансовая деятельность» (`okFin002`); перемещения исключены
- **Мягкое правило `aucard`** (`soft:true`): карты/касса, относящиеся только к АУ/САУ (`AU_CARDS`: СберБанк-1638 Елисеев, СберБанк-8572 Гарин, АльфаБанк-6170 / СовкомБанк-1673 Кольцова, Тинькофф-9930 Гарин, КМ-Касса; матч `isAuCard` по `norm(COL.ACCOUNT)`) → направление должно быть АУ/САУ (`isAuSauDir`). Мягкое = янтарная подсветка + пометка «мягкое» (вместо красного), но в KPI считается. Read-only
- **Структурное правило `movebal`** (флаг `group:true`, считается отдельным блоком, не через checks): перемещение должно быть парой +X/−X в колонке ПОСТУПЛЕНИЕ, сумма = 0. Группировка по дате ДДС + |сумме|; флаги: оформлено в «Списание», нулевое перемещение, нет пары / сумма группы ≠ 0
- KPI: Нарушений всего + по каждому правилу. Фильтры: даты / **Правило** (`_tabFilters.anomaly.field` = id правила или ''). Поля `minConf` в состоянии не используются (остались от старой версии)

Блок детализации направления (`dirDetails` в `leadgenCard`) показывает агентские комиссии + штат, если у направления есть fee/staff. `bflDeptCalc` при `Array.isArray(d.leadgen)`: `leadSpend`=Σ переменные (закупка+агентам), `qualTotal`=Σ квал-лиды, `leadTotalCost`=Σ dirCost, `fot`=общий ОМ (`roles[]`) + Σ штат направлений, `gross`=ФОТ+начисления+leadSpend+прочее, **база ЦКП = qualTotal** (ЦКП = стоимость квал-лида с учётом ФОТ ОМ). Сид: #1 из эталона (1380/50%/1350 → 690 квал, ЦКП 2700), #2-4 и ставки ОМ = 0 (плейсхолдеры, пользователь вводит) - поэтому расходы маркетинга = 1 863 000 как в эталоне, AC5/AC10 сохранены. - **База ЦКП ОС = сделки от ОП** (`tskpFromOp:true`): `bflOpDeals()` = выход отдела продаж; в `bflDeptCalc` `base = tskpFromOp ? bflOpDeals() : tskpBase`; ЦКП ОС = расходы / сделки от ОП (read-only база в карточке)
- **Расчётные налоги АУП** (от выручки `bflRevenue`): **НДС** (`cost.vatOfRevenue`) = `vat`×выручка; **Налог на прибыль** (`cost.profitTaxAuto`) = `profitTaxRate`×выручка + `profitTaxExtra`×max(0,выручка−`profitTaxThreshold`) (льготный УСН 1% + 1% свыше 300к по ФСС). Параметры в `global`; в таблице затрат - read-only «(расчёт)». `ca(c)` в `bflDeptCalc` считает эффективную сумму; `bflRevenue` не вызывает расчёт management (нет цикла)
- **Стоимость сделки по направлениям** (`bflDealCostByDir()`, таблица в шапке Коммерческого блока): на каждое направление = расходы маркетинга направления (`dirCost` из `leadRows`) + доля ФОТ КО и ОП, разнесённая пропорционально выходу направления (встречи КО / сделки ОП), ÷ сделки направления. Σ по направлениям = `com.gross`, Σ сделок = `com.deals`, блендед = `com.tskpDeal` (read-only, сходится). Направления переименованы: #1 «Лидогенерация» (было Маркетинг), #3 «Рекомендации ОКС» (было Рекомендации) - в leadgen + КО/ОП byDir + миграция
- **`bflCommercial()`** - агрегат коммерческого блока (Привлечение+Продажи): {gross, deals, suma (договорная), firstPay, **rass** (рассрочка ОКС в МЕСЯЦ - установившийся режим: N когорт платят одновременно = полная месячная рассрочка = (договорная−первый платёж)×collectionRate), rassMonths, rassPerClient, **rassPerClientMonth** (платёж клиента в месяц = (чек−первый платёж)/rassMonths), **tskpDeal = gross/deals = «Стоимость сделки»**}. Рассрочку собирает **ОКС** (бывш. ОС). В месячной юнитке ОКС собирает полную месячную рассрочку (не 1/N), т.к. одновременно платят N когорт
- **Средний чек в ОП** (`funnel.money:true`, по направлениям `byDir[].check`): «Сумма сделок (договорная)» = Σ сделки × чек (`R.suma`, `c.sumaTotal`); колонки «Средний чек»/«Сумма сделок» в таблице воронки + метрика в шапке. ⚠ Это **договорная** (booked) сумма, НЕ инкассация - деньги собираются во времени (первый платёж ОП + рассрочка ОС); инкассация задаётся отдельно (`incassation`). Сид чеков: #1 224000, #2 214800, #3/#4 245991. `bflEnsureModel` добавляет `money`/`check` в сохранённый ОП
- **Кол-во сделок для агентской комиссии #2 берётся из ОП** (а не вручную): `bflQtyFlow()` - forward-проход КОЛИЧЕСТВ по направлениям (маркетинг квал-лиды → КО встречи → ОП сделки) БЕЗ затрат, чтобы агентское вознаграждение читало сделки из ОП без зацикливания. В `bflDeptCalc` leadgen: `dealsInherited = feePerDeal && есть dealStage` → `deals = bflQtyFlow()[ОП.id][dir]`; в карточке «Сделки N (из ОП)» read-only. `agent_s2` (Агентская сеть этап 2) - легаси v1.0, **удалён** (агентская сеть = направление #2 через Маркетинг→КО→ОП); `bflEnsureModel` убирает его из старых моделей
- **Наследование потока (§3.2)**: выход отдела = вход следующего. `bflUpstreamOutput(id)` (сумма) и **`bflUpstreamOutputByDir(id)`** (карта `{dir:выход}` по направлениям): маркетинг → квал-лиды по направлениям (из `leadRows`), воронка → выход по направлениям (из `funnelRows`). **Воронка-стадия** (отдел с объектом `funnel`, спецкарточка `funnelCard`): база ЦКП = output; необходимая ШЕ = inflow/`funnel.norm`. **Конверсия РАЗНАЯ по направлениям** (`funnel.byDir`=[{dir,name,conv,otval}]): для каждого направления `inflowDir` наследуется раздельно (`bflUpstreamOutputByDir`), `outputDir`=inflowDir×conv×(1−otval); `inflow/output` = суммы; `funnelRows` - разбивка для карточки (таблица Направление × вход/конверсия/отвал/назначенные/выход). Без `byDir` - старый одиночный режим (back-compat). Пример: **Клиентский отдел (КО)** `funnel{inflowFrom:'marketing', byDir:[ofbfl 0.749/0.40, Agbfl 0.83/0.30, R-bfl 0.85/0.20, OP-bfl 0.85/0.20], norm:115}` - квал-лиды каждого направления (от ОМ) → своя конверсия во встречу → состоявшиеся встречи; #1 эталон 690→310 (ЦКП 3530). Меняешь маркетинг - вход КО пересчитывается живьём по направлениям. conv/otval - в % (`data-pct`). ⚠ Старые отделы `leadgen_ko`/`agent_s1` удалены (заменены на `marketing`); `bflEnsureModel` НЕ переносит отделы, которых нет в дефолте, и обновляет КО на `byDir`-структуру
- **«ОПИУ» (слой C, `bflRenderOpiu`, `bflOPIU`)**: Выручка = Σ инкассаций (ОП-KO 8.4М + ОП-AC 1.95М + ОС 23.753М) = 34 103 040; Расходы = Σ отделов (gross) + менеджмент; Сальдо/Рентабельность; таблица по отделам + **сверка с эталоном** §10. Тумблер «Исключить депозит (pass-through)» (`depositExcluded`) переключает расходы gross↔net
- **Вид сотрудничества (начисления per-role)**: у каждой роли штатного расписания поле `emp` - селект «Вид сотрудничества» в `staffTbl`: `official` (Официальное, ndfl+fss ≈43%, дефолт) / `ip` (ИП/Самозанятый, 7%) / `none` (Без трудоустройства, 0%). `bflRoleNachRate(r)` - ставка по виду (0 при галочке «убрать налоги»); `bflRolesNach(roles)` = Σ fte×rate×ставка. В `bflDeptCalc` начисления считаются per-role (`nachAcc` = осн. роли + штат направлений leadgen), НЕ `fot×единая_ставка`. staffTbl показывает эффективный % (`nach/fot`); АУП-чип - тоже эффективный. Остаются ФОТ (roles) + прямые (депозит, публикации, адвокатский запрет, налоги/НДС/аутсорсинг).
